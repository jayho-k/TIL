# Mem0 기반 에이전트 메모리 아키텍처

> 조사 기준일: 2026-07-12  
> 목적: Mem0를 중심으로 한 에이전트 메모리의 책임 경계와 도입 결정을 학습 노트로 정리한다.

## 결론

이 구성에서 Mem0는 모든 컨텍스트를 관리하는 플랫폼이 아니라, 대화와 에이전트 결과에서 재사용 가능한 사실을 뽑아 장기적으로 검색하는 **durable fact memory 엔진**이다.

```text
사용자 요청
  -> LangGraph: 상태 전이, 승인, 재시도, 장기 실행 제어
  -> DeepAgents: 계획, 도구 사용, 서브에이전트, 작업 파일
  -> MemoryService: 인증·권한, scope 강제, 정책·승격·충돌 결정
  -> Mem0: fact 추출, embedding, hybrid recall, explicit CRUD
  -> Qdrant: memory/entity 검색 인덱스

PostgreSQL: 메모리의 소유권·현재 상태·감사·명령·정책
MinIO: 원문 transcript·첨부·근거 snapshot·평가 데이터셋
```

## 구성 요소별 역할

| 구성 요소 | 맡는 일 | 맡기지 않는 일 |
| --- | --- | --- |
| Mem0 | fact 후보 추출, 관련 memory 검색, 명시적 update/delete | 테넌트 권한, 원문 보관, 충돌의 최종 판정 |
| Qdrant | dense/BM25 sparse vector 및 entity collection 검색 | business state와 감사의 원장 |
| PostgreSQL | `memory_nodes`, command/audit, 현재 상태, 승격·정책 | 대용량 원문 object storage |
| MinIO | transcript, attachment, evidence bundle, export | vector recall |
| DeepAgents | 계획·도구·서브에이전트·working file을 통한 실행 | durable memory의 source of truth |
| LangGraph | state, conditional edge, interrupt, retry/approval 흐름 | memory index와 권한 정책 |

Mem0에 Qdrant 외 저장소를 연결했다고 해서 이 책임이 사라지지는 않는다. 특히 Mem0의 identifier filter는 호출자의 identity를 `tenant_id`나 `project_id`에 자동 결속하는 authorization 기능이 아니다. 모든 MemoryService 요청은 서버가 결정한 scope filter를 반드시 포함해야 한다.

## 저장 경계

```text
Qdrant
  chat_portal_mem0             # memory text, vector, 검색용 payload
  chat_portal_mem0_entities    # entity와 linked memory id

PostgreSQL
  memory_nodes                 # Mem0 id, URI/path, active/superseded 상태
  memory_commands              # idempotency, add/update/delete 감사
  memory_evidence_refs         # MinIO object와 turn/line 근거 연결
  memory_promotions            # L1 -> L2/L3 승격·충돌 검토
  memory_provider_runs         # provider/LLM/vector 호출과 재시도 결과

MinIO
  raw transcript / attachment / evidence snapshot / evaluation dataset
```

Qdrant payload에는 MinIO 원문을 복사하지 않고 immutable `source_evidence_id` 또는 `source_ref`만 둔다. memory text를 뒷받침하는 근거와 검색 인덱스를 분리해야 보존·삭제·감사를 독립적으로 처리할 수 있다.

## 계층과 life cycle

| 계층 | 예 | 권위 저장소 | Mem0 recall |
| --- | --- | --- | --- |
| L0 Runtime | 현재 작업의 scratchpad, 서브에이전트 중간 결과 | DeepAgent state | 기본적으로 저장하지 않음 |
| L1 Working | 단기간 재사용할 작업 사실 | PostgreSQL + Qdrant | TTL을 둔 선택적 recall |
| L2 Project | 프로젝트 규칙, 결정, convention | PostgreSQL current state + MinIO evidence | 사용 |
| L3 User/Org | 사용자 선호, 조직 정책 | PostgreSQL current state + MinIO evidence | 사용 |

`Mem0.add()`의 성공은 L2/L3 사실의 확정이 아니다. candidate를 만들고 근거·scope·충돌을 검토한 뒤에만 control plane이 `active`, `superseded`, `rejected` 상태를 결정한다.

## DeepAgents·LangGraph 연결

기존 [LangGraph 노트](../../agent/text/04_langgraph.md)의 state/conditional edge와 [Deep Agent 노트](../../agent/text/07_deep-agent.md)의 context offloading을 아래처럼 결합한다.

```text
LangGraph request workflow
  -> MemoryService가 L3 -> L2 -> L1 순으로 strict filter recall
  -> provenance·score·policy로 후보 정리
  -> DeepAgents working file 생성
       /context/memory/00_org_policy.md
       /context/memory/10_project_facts.md
       /context/memory/20_user_preferences.md
       /context/memory/30_working_recall.md
  -> agent/subagent 실행
  -> memory candidate event 발행
  -> LangGraph의 review/promotion 노드가 승인·재시도·outbox 처리
  -> Mem0 explicit operation 및 PostgreSQL 상태 갱신
```

에이전트에 Mem0 CRUD tool을 무제한 노출하지 않는다. MemoryService가 authorization, 필수 metadata, 근거 연결, idempotency를 먼저 수행한다.

## 설계 규칙

1. Qdrant의 기존 document RAG collection과 Mem0 collection을 공유하지 않는다.
2. 모든 search에는 `tenant_id`와 최소 하나의 user/project/agent scope를 넣는다.
3. Mem0의 entity linking은 graph traversal이 아니다. 문서 관계 graph가 필요한 요구는 별도 RAG/graph 문제로 판단한다.
4. agent 또는 subagent의 산출물은 우선 L0 artifact로 둔다. 재사용성·성공·근거 조건을 통과한 것만 L2/L3 후보로 승격한다.
5. Mem0/Qdrant 장애 시에도 일반 대화가 가능한지 fallback 정책을 PoC에서 검증한다.
