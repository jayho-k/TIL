# 리랭커 강화 검색

> 원문: 사용자가 제공한 Mem0 문서 `Reranker-Enhanced Search`  
> 원문 제공일: 2026-07-18  
> 문서 인덱스: 전체 문서 인덱스는 <https://docs.mem0.ai/llms.txt>에서 가져올 수 있으며, 이 파일로 사용 가능한 모든 페이지를 찾을 수 있다.

> 리랭킹 모델로 vector hit의 순서를 다시 매겨 관련성을 높인다.

리랭커 강화 검색은 vector retrieval 이후 두 번째 scoring pass를 추가한다. 그 결과 Mem0는 가장 관련성 높은 memory를 먼저 반환할 수 있다. keyword 유사성만으로 뉘앙스를 놓치거나, agent 의사결정에 최고 신뢰도의 context가 필요할 때 활성화한다.

> **다음 상황에서 사용한다.**
>
> - 질의가 미묘하며 vector distance를 넘어서는 semantic understanding이 필요하다.
> - 큰 memory collection에서 수동으로 검토하기에는 near match가 너무 많이 나온다.
> - 전용 모델에 ranking을 위임하여 provider 간 일관된 scoring을 원한다.

> 경고: reranking은 latency를 높이고 hosted model에서는 API 비용도 늘린다. production traffic으로 benchmark하고 latency 민감 요청을 위한 fallback 경로를 정의한다.

> 참고: 아래 `설정`과 `동작 예시` snippet은 Python SDK를 사용한다. self-hosted **TypeScript SDK**는 Cohere, Zero Entropy, Sentence Transformer, Hugging Face, LLM reranker를 지원한다. [TypeScript SDK](#typescript-sdk)를 참고한다.

---

## TypeScript SDK

self-hosted TypeScript SDK(`mem0ai/oss`)는 **Cohere**, **Zero Entropy**, **Sentence Transformer**, **Hugging Face**, **LLM reranker** 다섯 가지 reranker를 제공한다. `reranker` 아래에 하나를 설정한 뒤 검색마다 `rerank: true`로 opt-in한다. key는 snake_case가 아니라 camelCase다. 즉 `api_key`가 아니라 `apiKey`를 쓴다.

provider SDK는 peer dependency다. 사용하는 reranker에 필요한 패키지를 설치한다.

```bash
pnpm add cohere-ai          # cohere
pnpm add zeroentropy        # zero_entropy
pnpm add @huggingface/transformers   # sentence_transformer, huggingface
# llm_reranker는 기본적으로 openai를 사용한다(이미 core dependency임).
# config.llm 아래에 다른 provider를 중첩할 때만 그 provider SDK를 설치한다.
```

### Hosted reranker(Cohere, Zero Entropy)

두 provider 모두 hosted API를 호출하며 config 또는 provider 환경 변수(`COHERE_API_KEY`, `ZERO_ENTROPY_API_KEY`)에서 key를 읽는다.

```typescript
import { Memory } from "mem0ai/oss";

// Cohere reranker(기본값: rerank-v3.5 모델)
const memory = new Memory({
  reranker: {
    provider: "cohere",
    config: { apiKey: process.env.COHERE_API_KEY },
  },
});

const results = await memory.search("내 음식 선호는 무엇인가요?", {
  filters: { userId: "alice" },
  rerank: true,
});
```

```typescript
// Zero Entropy reranker(기본값: zerank-1 모델)
const memory = new Memory({
  reranker: {
    provider: "zero_entropy",
    config: { apiKey: process.env.ZERO_ENTROPY_API_KEY },
  },
});
```

### Local cross-encoder(Sentence Transformer, Hugging Face)

두 provider 모두 [Transformers.js](https://huggingface.co/docs/transformers.js)로 cross-encoder를 로컬에서 실행한다. API key가 필요 없고 inference 시 네트워크도 사용하지 않는다. Transformers.js는 ONNX weight를 사용하므로 기본 모델은 Python SDK 기본값의 ONNX mirror다(`sentence_transformer` → `Xenova/ms-marco-MiniLM-L-6-v2`, `huggingface` → `Xenova/bge-reranker-base`). 다른 모델을 쓰려면 Hub의 ONNX-exported cross-encoder를 `model`에 지정한다.

```typescript
const memory = new Memory({
  reranker: {
    provider: "sentence_transformer", // 또는 "huggingface"
    config: {
      // model: "Xenova/bge-reranker-base",  // 기본값을 재정의
      device: "cpu", // Transformers.js device: "cpu" | "wasm" | "webgpu"
      maxLength: 512, // query-document pair당 최대 token 수
      normalize: true, // logit을 [0, 1]로 sigmoid-normalize(기본값)
    },
  },
});

const results = await memory.search("내가 좋아하는 영화는 무엇인가요?", {
  filters: { userId: "alice" },
  rerank: true,
});
```

> 참고: `batchSize`, `showProgressBar`는 Python SDK와의 config parity를 위해 허용되지만 이 runtime에서는 no-op이다. memory 검색은 작은 candidate set을 단일 in-process forward pass로 rerank하기 때문이다. 모델은 첫 사용 시 한 번 내려받으며 process 내에서 cache된다.

### LLM reranker

전용 reranker 대신 LLM으로 점수를 매기려면 `llm_reranker` provider를 사용한다. Memory의 주 `llm`을 재사용하지 않고 reranker config에서 별도의 LLM을 생성한다. 기본값은 `openai` / `gpt-4o-mini`다.

```typescript
const memory = new Memory({
  reranker: {
    provider: "llm_reranker",
    config: { apiKey: process.env.OPENAI_API_KEY },
  },
});

const results = await memory.search("내가 좋아하는 영화는 무엇인가요?", {
  filters: { userId: "alice" },
  rerank: true,
});
```

기본값을 바꾸려면 `config.llm` 아래에 다른 provider를 중첩한다.

```typescript
const memory = new Memory({
  reranker: {
    provider: "llm_reranker",
    config: {
      llm: {
        provider: "anthropic",
        config: { apiKey: process.env.ANTHROPIC_API_KEY },
      },
    },
  },
});
```

### Config 참조

| Provider | 기본 모델 | 주요 config field |
| --- | --- | --- |
| `cohere` | `rerank-v3.5` | `apiKey`, `model`, `topK` |
| `zero_entropy` | `zerank-1` | `apiKey`, `model`, `topK` |
| `sentence_transformer` | `Xenova/ms-marco-MiniLM-L-6-v2` | `model`, `device`, `maxLength`, `normalize`, `topK` |
| `huggingface` | `Xenova/bge-reranker-base` | `model`, `device`, `maxLength`, `normalize`, `topK` |
| `llm_reranker` | `openai` / `gpt-4o-mini` | `provider`, `model`, `apiKey`, `llm`(중첩 재정의), `topK` |

> 참고: `rerank`는 검색마다 opt-in하며 `reranker`를 설정하지 않았으면 no-op이다. reranker 호출이 실패하면 Mem0는 warning을 기록하고 원래 vector-ranked 결과를 반환한다.

## 기능 구성

- **초기 vector 검색:** 유사도를 기준으로 candidate memory를 가져온다.
- **Reranker pass:** 특화된 모델이 원래 질의에 대한 각 candidate의 점수를 매긴다.
- **재정렬된 결과:** Mem0는 reranker score로 응답을 정렬한 후 반환한다.
- **선택적 fallback:** 요청마다 reranking을 켜거나, 성능·비용이 우려되면 완전히 끌 수 있다.

### 지원 provider

- **[Cohere](/components/rerankers/models/cohere):** API 기반 scoring을 사용하는 다국어 hosted reranker
- **[Sentence Transformer](/components/rerankers/models/sentence_transformer):** GPU 또는 CPU용 로컬 Hugging Face cross-encoder
- **[Hugging Face](/components/rerankers/models/huggingface):** hosted 또는 on-prem reranker model ID를 자유롭게 사용
- **[LLM Reranker](/components/rerankers/models/llm_reranker):** 선호하는 LLM(OpenAI 등)을 prompt-driven scoring에 사용
- **[Zero Entropy](/components/rerankers/models/zero_entropy):** retrieval task에 맞춰 조정된 고품질 neural reranking

### Provider 비교

| Provider | Latency | 품질 | 비용 | 로컬 배포 |
| --- | --- | --- | --- | --- |
| Cohere | 중간 | 높음 | API 비용 | ❌ |
| Sentence Transformer | 낮음 | 좋음 | 무료 | ✅ |
| Hugging Face | 낮음~중간 | 가변적 | 무료 | ✅ |
| LLM Reranker | 높음 | 매우 높음 | API 비용 | 상황에 따라 다름 |

### Async 지원

```python
from mem0 import AsyncMemory

async_memory = AsyncMemory.from_config(config)

async def search_with_rerank():
    return await async_memory.search(
        "내 선호는 무엇인가요?",
        filters={"user_id": "alice"},
        rerank=True
    )

import asyncio
results = asyncio.run(search_with_rerank())
```

> 확인: async 응답을 검사하여 reranking이 계속 적용됐는지 확인한다. score는 synchronous 구현과 일치해야 한다.

### 성능과 비용 조정

```python
# GPU 친화적인 로컬 reranker 설정
config = {
    "reranker": {
        "provider": "sentence_transformer",
        "config": {
            "model": "cross-encoder/ms-marco-MiniLM-L-6-v2",
            "device": "cuda",
            "batch_size": 32,
            "top_k": 10,
            "max_length": 256
        }
    }
}

# hosted reranker의 스마트 토글
def smart_search(query, user_id, use_rerank=None):
    if use_rerank is None:
        use_rerank = len(query.split()) > 3
    return m.search(query, filters={"user_id": user_id}, rerank=use_rerank)
```

> 팁: query length, user tier 같은 heuristic으로 rerank 여부를 정한다. 그러면 모든 요청에 부담을 주지 않고 high-signal query가 이점을 얻는다.

### 실패를 우아하게 처리하기

```python
try:
    results = m.search("test query", filters={"user_id": "alice"}, rerank=True)
except Exception as exc:
    print(f"Reranking failed: {exc}")
    results = m.search("test query", filters={"user_id": "alice"}, rerank=False)
```

> 경고: 항상 vector-only 검색으로 fallback한다. query를 버리는 것은 순서가 약간 덜 관련성 높아지는 것보다 훨씬 큰 정확도 문제를 일으킨다.

### v0.x에서 마이그레이션

```python
# 이전: 기본 vector 검색
results = m.search("query", filters={"user_id": "alice"})

# 이후: config로 reranking을 활성화한 같은 API
config = {
    "reranker": {
        "provider": "sentence_transformer",
        "config": {
            "model": "cross-encoder/ms-marco-MiniLM-L-6-v2"
        }
    }
}

m = Memory.from_config(config)
results = m.search("query", filters={"user_id": "alice"})
```

## 동작 예시

### 기본 reranked 검색

```python
results = m.search(
    "내 음식 선호는 무엇인가요?",
    filters={"user_id": "alice"}
)

for result in results["results"]:
    print(f"Memory: {result['memory']}")
    print(f"Score: {result['score']}")
```

> 확인: 각 결과는 reranker로 조정된 score를 표시해야 하므로, baseline vector 결과와 순서를 비교할 수 있다.

### 요청별 reranking 토글

```python
results_with_rerank = m.search(
    "내가 좋아하는 영화는 무엇인가요?",
    filters={"user_id": "alice"},
    rerank=True
)

results_without_rerank = m.search(
    "내가 좋아하는 영화는 무엇인가요?",
    filters={"user_id": "alice"},
    rerank=False
)
```

> 팁: rollout 중에는 reranked와 non-reranked 목록을 기록해 stakeholder가 모든 곳에 강제하기 전에 개선을 볼 수 있게 한다.

> 확인: 두 목록에서 같은 memory를 볼 수 있지만, reranked 응답은 semantic relevance에 따라 순서를 다시 매긴다.

### 메타데이터 filter와 조합

```python
results = m.search(
    "중요한 업무 task",
    filters={
        "AND": [
            {"user_id": "alice"},
            {"category": "work"},
            {"priority": {"gte": 7}}
        ]
    },
    rerank=True,
    top_k=20
)
```

> 확인: filter가 적용된 reranked 검색도 모든 metadata 절을 계속 준수하는지 확인한다. reranking은 candidate의 순서만 바꾸며 filter를 우회하지 않는다.

### 실제 사용 playbook

#### 고객 지원

```python
config = {
    "reranker": {
        "provider": "cohere",
        "config": {
            "model": "rerank-v3.5",
            "api_key": "your-cohere-api-key"
        }
    }
}

m = Memory.from_config(config)

results = m.search(
    "모바일 앱 login issue가 있는 고객",
    filters={"agent_id": "support_bot", "category": "technical_support"},
    rerank=True
)
```

> 확인: 상위 결과는 login issue 문맥과 일치하는 ticket을 강조해야 하므로 agent가 더 빨리 응답할 수 있다.

#### 콘텐츠 추천

```python
results = m.search(
    "우주 탐사 주제의 science fiction 책",
    filters={"user_id": "reader123", "content_type": "book_recommendation"},
    rerank=True,
    top_k=10
)

for result in results["results"]:
    print(f"Recommendation: {result['memory']}")
    print(f"Relevance: {result['score']:.3f}")
```

> 확인: 요청한 theme와 적용한 metadata limit 모두에 맞는 high-scoring 추천이 나와야 한다.

#### 개인 비서

```python
results = m.search(
    "지난달에 즐겼고 채식 선택지가 좋았던 restaurant는 무엇인가요?",
    filters={
        "AND": [
            {"user_id": "foodie_user"},
            {"category": "dining"},
            {"rating": {"gte": 4}},
            {"date": {"gte": "2024-01-01"}}
        ]
    },
    rerank=True
)
```

> 팁: 다른 lifestyle query에도 이 pattern을 재사용한다. rerank config는 바꾸지 않고 filter와 prompt text만 교체한다.

> 참고: 각 workflow는 같은 `m.search(...)` signature를 유지한다. 따라서 prompt와 filter만 바꾸어 여러 agent에서 이 query를 template으로 만들 수 있다.

## 기능이 동작하는지 검증하기

- 결과 payload에서 vector `score`와 reranker score를 모두 검사한다. field가 일치하지 않으면 reranker가 실행되지 않았음을 의미한다.
- reranking 활성화 전후의 latency를 추적하여 SLA를 지키는지 확인한다.
- throttling 또는 quota warning이 있는지 provider log나 dashboard를 검토한다.
- reranked 응답을 기본값으로 두기 전에 A/B 비교(rerank on/off)로 관련성 향상을 검증한다.

## 모범 사례

1. **로컬에서 시작한다.** hosted API 비용을 내기 전에 Sentence Transformer model로 가치를 증명한다.
2. **Latency를 모니터링한다.** reranker duration metric을 추가해 regression을 빠르게 발견한다.
3. **비용을 통제한다.** `top_k`와 선택적 toggle을 사용해 hosted reranker 비용의 상한을 둔다.
4. **Fallback을 유지한다.** reranker failure는 항상 잡고 vector-only ordering으로 계속 진행한다.
5. **자주 실험한다.** domain과 language mix에 가장 잘 맞는 provider/model을 찾기 위해 교체해 본다.
