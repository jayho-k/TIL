# V3 쓰기 파이프라인: `Memory.add()`에서 사실 메모리가 만들어지는 과정

> 분석 대상: `mem0/memory/main.py`의 `Memory.add()`, `Memory._add_to_vector_store()` 및 AsyncMemory의 대응 구현  
> 보조 대상: `mem0/memory/storage.py`, `mem0/memory/utils.py`, `mem0/configs/prompts.py`  
> 기준 snapshot: `mem0ai 2.0.12` (upstream commit 미확인)

## 결론

기본값인 `Memory.add(..., infer=True)`는 입력 대화를 Qdrant에 그대로 넣는 함수가 아니다. 입력과 세션 범위를 정규화하고, 최근 대화와 관련 기존 메모리를 LLM prompt에 넣어 새 사실을 추출한 뒤, 새 UUID·embedding·payload를 만들어 여러 저장소에 순서대로 기록하는 **메모리 생성 orchestration pipeline**이다.

```text
add(messages, scope, metadata, infer=True)
  │
  ├─ 입력 검증 / scope와 저장 metadata 생성 / vision 전처리
  │
  ├─ SQLite messages ─────────────► last_messages 최대 10개
  ├─ 새 messages 문자열화 ────────► parsed_messages
  ├─ Qdrant dense search ─────────► existing_results 최대 10개
  │                                  └─ 실제 UUID를 "0", "1"로 치환
  │
  ├─ LLM 1회 호출 ────────────────► {"memory": [{"text": ...}, ...]}
  ├─ 추출 text batch embedding
  ├─ 새 UUID / payload 생성 / MD5 exact dedup
  │
  ├─ Qdrant main collection insert
  ├─ SQLite history ADD 기록
  ├─ entity collection 연결
  └─ SQLite messages 저장 후 ADD 결과 반환
```

한 번의 호출이 다음 세 저장 영역을 변경하지만, 이를 묶는 트랜잭션은 없다.

| 저장 영역 | 저장 내용 | 목적 |
| --- | --- | --- |
| main vector collection | 추출된 사실, dense vector, 가능한 경우 BM25 sparse vector, metadata | 장기 사실 검색 |
| entity collection | entity 문자열과 관련 main-memory UUID 목록 | entity 기반 검색 boost |
| SQLite | ADD history와 최근 세션 메시지 | 감사 이력과 다음 추출의 단기 문맥 |

또한 prompt가 의도하는 LLM 직접 memory linking과 실제 구현을 구분해야 한다. 기존 UUID를 임시 ID로 바꾸는 `uuid_mapping`은 생성되지만 이후 사용되지 않고, LLM 응답의 `linked_memory_ids`도 저장되지 않는다. 현재 실제 연결은 Phase 7의 entity collection이 담당한다.

## 1. `add()` 입력 정규화와 route

일반적인 입력은 다음과 같다.

```python
result = memory.add(
    messages=[
        {"role": "user", "content": "우리는 Qdrant를 사용하기로 결정했다."},
        {"role": "assistant", "content": "결정 사항을 기억하겠다."},
    ],
    user_id="alice",
    agent_id="research-agent",
    run_id="run-001",
    metadata={"project_id": "memory-poc", "source": "meeting"},
    infer=True,
)
```

### 1.1 메시지 정규화

`messages`는 `str`, `dict`, `list`만 받는다.

| 입력 | 내부 변환 |
| --- | --- |
| `"hello"` | `[ {"role": "user", "content": "hello"} ]` |
| `{...}` | `[ {...} ]` |
| `list` | 그대로 사용. list 원소의 schema는 이 시점에 일괄 검증하지 않음 |
| 그 외 타입 | `Mem0ValidationError`, code `VALIDATION_003` |

list 원소가 dict인지, `role`과 `content`가 있는지는 `add()` 입구에서 완전히 검증되지 않는다. `infer=False`는 잘못된 항목을 개별적으로 건너뛰지만, `infer=True`에서는 이후 `parse_vision_messages()`나 `parse_messages()`에서 `.get()`을 호출하므로 비-dict 원소가 예외를 만들 수 있다.

### 1.2 저장 metadata와 query filter는 서로 다른 dict다

`_build_filters_and_metadata()`는 두 값을 만든다.

```python
processed_metadata = {
    "project_id": "memory-poc",
    "source": "meeting",
    "user_id": "alice",
    "agent_id": "research-agent",
    "run_id": "run-001",
}

effective_filters = {
    "user_id": "alice",
    "agent_id": "research-agent",
    "run_id": "run-001",
}
```

- `processed_metadata`는 새 main-memory payload의 template이다. 사용자 metadata와 scope ID를 포함한다.
- `effective_filters`는 기존 memory/entity를 조회할 scope다.
- `user_id`, `agent_id`, `run_id` 중 적어도 하나가 없으면 `VALIDATION_001` 오류가 난다.
- ID는 trim되며 빈 문자열이나 공백-only 값은 거부된다.
- `expiration_date`가 있으면 정규화 후 `processed_metadata`에만 추가된다.

Phase 1과 Phase 7은 `effective_filters`에서도 `user_id`, `agent_id`, `run_id`만 다시 추린다. 따라서 `metadata={"project_id": ...}`를 넘겨도 관련 기존 메모리를 검색할 때 `project_id`로 범위를 좁히지 않는다. 사용자 metadata는 저장 payload에는 들어가지만 V3 add의 dedup-context 조회 조건은 아니다.

### 1.3 `session_scope`는 SQLite 최근 대화의 partition key다

scope ID를 key 이름 순서로 이어 붙인다.

```text
agent_id=research-agent&run_id=run-001&user_id=alice
```

이 문자열은 Qdrant point ID가 아니라 SQLite `messages.session_scope`에 사용된다. ID 조합이 하나라도 달라지면 별도의 최근 대화 문맥으로 취급한다.

### 1.4 vision 전처리 후의 메시지가 실제 pipeline 입력이다

`add()`는 `_add_to_vector_store()` 전에 `parse_vision_messages()`를 호출한다.

- `enable_vision=True`: image message를 vision LLM으로 설명한 텍스트로 바꾼다.
- vision이 꺼진 상태의 text+image list: text part만 합치고 image part는 버린다.
- vision이 꺼진 image-only message: 해당 message를 버린다.
- `content=None`인 assistant tool-call message: 버린다.

따라서 Phase 8에서 SQLite에 저장하는 `messages`도 API에 들어온 원본과 항상 같지 않다. 이미지가 vision description으로 바뀌었거나 일부 message가 제거된 **전처리 결과**다.

### 1.5 세 갈래의 저장 경로

| 조건 | 경로 | LLM fact extraction | recent messages | entity linking |
| --- | --- | --- | --- | --- |
| 일반 `infer=True` | V3 8-phase pipeline | 사용 | 사용 | 사용 |
| `infer=False` | message별 `_create_memory()` | 미사용 | 미사용 | 미사용 |
| `memory_type="procedural_memory"` + `agent_id` | 대화 전체를 한 개 procedural summary로 저장 | 별도 LLM 요약 | 미사용 | 미사용 |

`memory_type="procedural_memory"`를 주고 `agent_id`를 생략하면 명시적 오류가 아니라 일반 V3 path로 내려간다. procedural memory를 기대한다면 wrapper에서 `agent_id` 필수 조건을 별도로 검증하는 편이 안전하다.

`timestamp`는 OSS `add()`에서 지원되지 않는다. 값이 들어오면 즉시 `ValueError`가 난다. 과거 transcript를 import해도 prompt builder에 별도 관찰 시각을 전달할 수 없으므로 상대 날짜는 실행 시점 기준으로 해석될 수 있다.

## 2. `infer=False`: 대화를 사실로 바꾸지 않는 raw 저장

`infer=False`는 system role을 제외한 각 message를 별도 memory로 저장한다.

```text
message
  → role/content 확인
  → role과 선택적 name(actor_id)을 payload에 추가
  → content embedding
  → 새 UUID와 payload 생성
  → main collection insert
  → SQLite history ADD
  → 결과 반환
```

예를 들어 다음 입력은 두 개의 main memory가 된다.

```python
[
    {"role": "user", "content": "Qdrant를 사용한다", "name": "alice"},
    {"role": "assistant", "content": "설정을 준비한다"},
]
```

`_create_memory()`가 만드는 payload는 V3 fact payload와 유사하다.

```python
{
    **processed_metadata,
    "role": "user",
    "actor_id": "alice",       # name이 있을 때
    "data": "Qdrant를 사용한다",
    "hash": "md5...",
    "text_lemmatized": "...",
    "created_at": "...",
    "updated_at": "...",
}
```

그러나 이 경로에는 다음 기능이 없다.

- LLM fact extraction과 의미 중복 억제
- SQLite 최근 메시지 저장
- entity extraction과 entity collection 연결
- batch embedding/insert
- MD5를 이용한 저장 전 중복 확인

`hash`는 payload에 기록될 뿐, `_create_memory()`에서 기존 hash를 조회해 중복을 거르지는 않는다. 동일 raw message를 두 번 넣으면 UUID가 다른 두 point가 생길 수 있다.

## 3. V3 pipeline의 중간 데이터 구조

Phase 설명을 읽기 전에 변수의 역할을 먼저 구분해야 한다.

| 변수 | 형태 | 만들어지는 곳 | 실제 용도 |
| --- | --- | --- | --- |
| `messages` | `list[dict]` | `add()` 정규화/vision 처리 | 이번 호출의 새 메시지 |
| `processed_metadata` | `dict` | `_build_filters_and_metadata()` | 새 main-memory payload template |
| `effective_filters` / `filters` | `dict` | 같은 함수 | scope 기반 기존 memory/entity 조회 |
| `session_scope` | `str` | Phase 0 | SQLite messages partition key |
| `last_messages` | `list[dict]` | SQLite 조회 | 대명사·생략된 문맥 해석용 prompt 입력 |
| `parsed_messages` | `str` | `parse_messages()` | dense query와 LLM `New Messages` 입력 |
| `existing_results` | vector-store result list | Phase 1 | 관련 기존 메모리, hash 문맥 |
| `existing_memories` | `[{id, text}]` | Phase 1 | LLM dedup/linking prompt 입력 |
| `uuid_mapping` | `{임시 ID: 실제 UUID}` | Phase 1 | 현재 구현에서는 생성 후 미사용 |
| `extracted_memories` | `list[dict]` 기대 | Phase 2 JSON parse | 새 사실 후보 |
| `embed_map` | `{text: dense vector}` | Phase 3 | 새 레코드 vector 생성 |
| `records` | `(uuid, text, vector, payload)` list | Phase 4·5 | Phase 6 이후 모든 저장/반환의 기준 |
| `global_entities` | `{normalized text: [type, text, memory_ids]}` | Phase 7 | entity 중복 병합과 연결 |

이 pipeline을 이해할 때 가장 중요한 경계는 `extracted_memories`와 `records` 사이에 있다. LLM이 출력한 object를 그대로 저장하지 않는다. 코드가 일부 필드만 읽고 새 UUID와 payload를 다시 만든 뒤 `records`로 변환한다.

## 4. `infer=True`: V3 8단계 파이프라인

### Phase 0 — 최근 세션 문맥과 새 메시지 문자열 만들기

```python
session_scope = _build_session_scope(filters)
last_messages = self.db.get_last_messages(session_scope, limit=10)
parsed_messages = parse_messages(messages)
```

#### 입력과 출력

`last_messages`의 실제 형태는 다음과 같다.

```python
[
    {
        "role": "user",
        "content": "그 프로젝트는 다음 주에 시작해",
        "name": None,
        "created_at": "2026-07-18T...",
    },
]
```

`parse_messages()`는 이번 호출의 message를 한 문자열로 합친다.

```text
user: 우리는 Qdrant를 사용하기로 결정했다.
assistant: 결정 사항을 기억하겠다.
```

- `system`, `user`, `assistant` role만 문자열에 포함한다.
- `content=None` 또는 알 수 없는 role은 포함하지 않는다.
- system message도 V3 prompt의 `New Messages`에 포함될 수 있다. 반면 `infer=False`는 system message를 명시적으로 건너뛴다.

#### 최근 10개의 정확한 의미

`limit=10`은 10턴이 아니라 SQLite row 10개다. user+assistant가 한 턴이라면 보통 약 5턴이다. prompt formatter는 과거 message 하나의 content를 최대 300자로 잘라 `Last k Messages` 섹션에 넣는다. 이번 호출의 `New Messages`는 이 300자 제한을 거치지 않는다.

조회 limit만 20으로 바꿔도 문맥이 늘어나지 않는다. `SQLiteManager.save_messages()`가 세션별 최근 10개를 제외한 행을 실제 삭제하기 때문이다. 늘리려면 sync/async 조회값과 SQLite retention을 함께 바꾸거나 두 값을 별도 설정으로 분리해야 한다.

#### 순서 보장의 문제

`save_messages()`는 한 호출의 모든 message에 동일한 `created_at`을 부여한다. eviction과 조회는 `created_at`만 정렬 기준으로 사용한다. 한 번에 10개보다 많은 transcript를 넣거나 timestamp 동률이 생기면 원래 입력 순서와 진짜 최신 N개를 보장하지 않는다. bulk import에는 증가 sequence나 message timestamp가 별도로 필요하다.

### Phase 1 — 관련 기존 메모리 조회와 임시 ID 변환

```python
search_filters = {
    k: v for k, v in filters.items()
    if k in ("user_id", "agent_id", "run_id") and v
}

query_embedding = self.embedding_model.embed(parsed_messages, "search")
existing_results = self.vector_store.search(
    query=parsed_messages,
    vectors=query_embedding,
    top_k=10,
    filters=search_filters,
)
```

#### 이 검색은 `Memory.search()`가 아니다

`self.vector_store.search()`를 직접 호출하므로 dense vector 결과 최대 10개만 가져온다. BM25, entity boost, reranker, `Memory.search()`의 over-fetch와 score fusion은 사용하지 않는다. 따라서 LLM이 보는 중복 판단 문맥은 V3 read pipeline보다 좁고 dense recall에 전적으로 의존한다.

Phase 1에 별도 try/except가 없기 때문에 query embedding이나 vector-store search가 실패하면 `add()`가 예외로 끝나고 이번 message도 SQLite recent context에 저장되지 않는다.

#### 실제 UUID를 임시 ID로 바꾸는 과정

Qdrant 결과가 다음과 같다고 가정한다.

```text
9f3a1d7c-... : 사용자는 PostgreSQL을 사용한다
a76bc210-... : 사용자는 Qdrant를 검토하고 있다
```

코드는 다음 두 값을 만든다.

```python
uuid_mapping = {
    "0": "9f3a1d7c-...",
    "1": "a76bc210-...",
}

existing_memories = [
    {"id": "0", "text": "사용자는 PostgreSQL을 사용한다"},
    {"id": "1", "text": "사용자는 Qdrant를 검토하고 있다"},
]
```

긴 UUID 대신 짧은 허용 목록 handle을 LLM에 주고, LLM이 `linked_memory_ids: ["1"]`을 반환하면 코드가 `uuid_mapping["1"]`로 실제 UUID를 복구하는 것이 일반적인 anti-hallucination 패턴이다. 이 방식은 UUID 한 글자 변경이나 존재하지 않는 UUID 생성을 막을 수 있다.

#### 현재 snapshot에서는 복원 단계가 없다

이 코드에서는 `uuid_mapping`이 이후 한 번도 읽히지 않는다. LLM이 반환한 `linked_memory_ids`도 Phase 4에서 소비하지 않는다. 따라서 소스의 `# Map UUIDs to integers (anti-hallucination)` 주석은 end-to-end로 완성된 기능 설명이 아니라 **구현 의도의 흔적**이다.

더구나 system prompt는 `Existing Memories`가 UUID를 가진다고 설명하지만 실제 입력은 임시 ID다. 새 extraction object의 `id`도 `"0"`, `"1"` 순번을 쓰므로 다음 두 ID 공간이 겹친다.

| ID | 뜻 | 이후 사용 여부 |
| --- | --- | --- |
| `existing_memories[].id="0"` | 기존 메모리를 가리키는 임시 handle | prompt에만 사용 |
| `extracted_memories[].id="0"` | 새 추출 결과의 순번 | 코드가 무시 |
| `uuid_mapping["0"]` | 기존 메모리의 실제 UUID | 생성 후 미사용 |
| Phase 4 `uuid.uuid4()` | 새 memory의 실제 UUID | main/history/entity/반환에 사용 |

임시 ID가 현재 주는 실질적인 효과는 LLM에게 기존 memory 목록을 짧은 형식으로 보여 주는 정도다. 직접 memory-to-memory link를 보존하지는 않는다.

### Phase 2 — prompt 조립과 LLM ADD-only 추출

#### system prompt 선택

기본 system prompt는 `ADDITIVE_EXTRACTION_PROMPT`다. scope가 `agent_id`만 있고 `user_id`가 없으면 `AGENT_CONTEXT_SUFFIX`를 덧붙인다.

```python
is_agent_scoped = bool(filters.get("agent_id")) and not filters.get("user_id")
```

`user_id`와 `agent_id`를 함께 주면 agent suffix를 사용하지 않는다.

호출별 `prompt` 인자는 system prompt를 교체하지 않는다.

```python
custom_instr = prompt or self.custom_instructions
```

이 값은 prompt builder의 `Custom Instructions` 섹션에 들어간다. 호출별 `prompt`가 truthy이면 config의 `custom_instructions`를 완전히 대체하며 둘을 합치지 않는다.

#### 실제 user prompt에 채워지는 섹션

`generate_additive_extraction_prompt()`는 여러 입력을 받을 수 있지만 V3 호출자는 네 값만 명시적으로 넘긴다.

| prompt 섹션 | 실제 값 |
| --- | --- |
| `Summary` | 전달하지 않으므로 빈 값 |
| `Last k Messages` | SQLite의 최근 최대 10개, 각 300자 제한 |
| `Recently Extracted Memories` | 전달하지 않으므로 `[]` |
| `Existing Memories` | dense top-10을 임시 ID로 변환한 목록 |
| `New Messages` | `parsed_messages` 문자열 |
| `Observation Date` | 인자를 주지 않아 실행 당시 UTC date |
| `Current Date` | 실행 당시 UTC date |
| `Custom Instructions` | 호출 `prompt` 또는 config 값이 있을 때 |
| `Language Requirement` | `use_input_language`를 넘기지 않아 비활성 |

system prompt 설명에는 최근 message와 recently-extracted memory가 최대 20개라고 쓰여 있지만 이 OSS 호출은 recent messages 10개만 읽고 recently-extracted memory는 넣지 않는다. Prompt의 기능 설명과 실제 호출 wiring을 동일한 것으로 보면 안 된다.

#### 기대 출력과 실제 소비 필드

LLM에는 `response_format={"type": "json_object"}`를 요청하며 다음 형태를 기대한다.

```json
{
  "memory": [
    {
      "id": "0",
      "text": "사용자는 Qdrant를 벡터 저장소로 사용하기로 결정했다",
      "linked_memory_ids": ["1"],
      "attributed_to": "user"
    }
  ]
}
```

그러나 이후 Python 코드가 실제 소비하는 필드는 다르다.

| LLM 출력 필드 | 처리 |
| --- | --- |
| `text` | 필수처럼 사용. embedding과 main-memory 본문이 됨 |
| `attributed_to` | truthy일 때 main payload에 복사 |
| `id` | 무시. 새 실제 UUID는 코드가 생성 |
| `linked_memory_ids` | 무시. `uuid_mapping` 복원도 없음 |
| `event` | 무시. V3 자동 path는 ADD-only |
| 그 외 key | 무시 |

따라서 LLM output object 전체가 저장되는 것이 아니다. `text`와 선택적 `attributed_to`만 다음 Phase로 넘어간다.

#### LLM 오류와 JSON 오류는 다르게 취급된다

```text
LLM provider 호출 실패
  → LLMError로 감싸 다시 발생
  → recent messages 저장 안 됨

LLM 응답은 왔지만 JSON parsing 실패
  → 로그 후 extracted_memories=[]
  → recent messages는 저장
  → add 결과는 빈 results
```

파싱 순서는 다음과 같다.

1. `remove_code_blocks()`로 바깥 code fence와 `<think>...</think>` 제거
2. `json.loads(..., strict=False)`
3. 실패하면 `extract_json()`으로 JSON처럼 보이는 구간을 잘라 재시도
4. root object의 `memory`를 읽음

`response_format`은 provider에 JSON object를 요청할 뿐 `memory: list[object]` schema를 Python에서 검증하지 않는다. 다음 응답은 JSON이지만 후속 처리에서 예외가 날 수 있다.

```json
{"memory": "not-a-list"}
```

```json
{"memory": ["not-an-object"]}
```

`normalize_facts()` helper가 별도 파일에 존재하지만 현재 V3 path는 이를 호출하지 않는다.

### Phase 3 — 추출된 `text`를 batch embedding

```python
mem_texts = [m.get("text", "") for m in extracted_memories if m.get("text")]
mem_embeddings_list = self.embedding_model.embed_batch(mem_texts, "add")
embed_map = dict(zip(mem_texts, mem_embeddings_list))
```

- `text`가 없거나 빈 값인 object는 embedding 대상에서 제외된다.
- batch embedding이 예외를 내면 text별 `embed()`로 fallback한다.
- 개별 embedding도 실패한 text는 `embed_map`에 들어가지 않아 저장 대상에서 빠진다.
- batch API가 예외 없이 입력보다 적은 vector를 반환하면 `zip()`이 조용히 잘라낸다. 잘린 text는 이후 저장되지 않으며 별도 warning이 없다.
- 같은 text가 여러 번 있으면 dict key 하나로 합쳐지지만, 다음 Phase의 MD5 batch dedup이 중복 record 생성을 막는다.

모든 text의 embedding이 실패하면 `records`가 비어 Phase 6으로 가지 않고 recent messages만 저장한 뒤 빈 결과를 반환한다.

### Phase 4·5 — LLM object를 실제 저장 record로 변환하고 중복 제거

#### 실제 record 생성

각 유효 text마다 코드가 새 UUID와 payload를 만든다.

```python
memory_id = str(uuid.uuid4())

payload = {
    **processed_metadata,
    "data": text,
    "text_lemmatized": lemmatize_for_bm25(text),
    "hash": hashlib.md5(text.encode()).hexdigest(),
    "created_at": "UTC ISO-8601",
    "updated_at": "UTC ISO-8601",
    # LLM이 넣었을 때만 attributed_to
}

record = (memory_id, text, embedding, payload)
```

`records`가 만들어진 이후 Phase 6 저장, Phase 7 entity link, Phase 8 응답은 모두 이 list를 기준으로 한다. LLM의 `id`나 `linked_memory_ids`는 이 경계를 통과하지 못한다.

#### 중복 제거는 세 종류지만 보장 수준이 다르다

1. **LLM 의미 중복 억제:** Existing Memories를 prompt에 보여 주고 같은 사실을 다시 뽑지 말라고 한다. 모델 판단이므로 보장되지 않는다.
2. **기존 hash 비교:** Phase 1 dense top-10 결과의 `hash`와 새 text MD5가 같으면 건너뛴다.
3. **현재 batch hash 비교:** 이번 응답 안에서 먼저 나온 동일 text MD5와 같으면 건너뛴다.

MD5 비교는 문자열 exact match다.

```text
"사용자는 커피를 좋아한다"
"사용자는 커피를 선호한다"
```

두 문장은 의미가 같아도 hash가 다르다. 또한 기존 hash 집합은 collection 전체가 아니라 Phase 1 dense top-10에서만 만든다. 멀리 떨어진 동일 text가 top-10에 들어오지 않으면 전역 exact duplicate도 막지 못한다.

### Phase 6 — main collection insert와 SQLite history

#### main vector store 쓰기

`records`의 vector, UUID, payload를 한 번에 insert한다.

```python
self.vector_store.insert(
    vectors=all_vectors,
    ids=all_ids,
    payloads=all_payloads,
)
```

batch insert가 실패하면 항목별 insert로 fallback한다. 하지만 개별 실패한 record를 `records`에서 제거하거나 성공 ID 집합을 따로 만들지 않는다.

```text
batch insert 실패
  ├─ record A 개별 insert 성공
  ├─ record B 개별 insert 실패 → error log만 남김
  └─ records에는 A와 B 모두 계속 존재
```

#### history 쓰기

코드는 원래 `records` 전체로 다음 history를 만든다.

```python
{
    "memory_id": record_uuid,
    "old_memory": None,
    "new_memory": text,
    "event": "ADD",
    "created_at": payload["created_at"],
    "is_deleted": 0,
}
```

`batch_add_history()`가 실패하면 history별 `add_history()`로 fallback한다. 개별 history 실패도 log만 남기고 pipeline은 계속된다.

#### 원자성과 false-success 문제

Qdrant와 SQLite를 묶는 트랜잭션이 없고 실제 insert 성공 집합을 추적하지 않으므로 다음 상태가 가능하다.

```text
main-memory B는 Qdrant insert 실패
  → SQLite history에는 B의 ADD가 기록됨
  → Phase 7 entity에는 B UUID가 연결됨
  → Phase 8 응답에도 B가 ADD 성공처럼 포함됨
```

반대 방향도 가능하다. Qdrant insert는 성공했지만 history가 실패하면 main memory는 존재하고 history만 없다. 따라서 `event="ADD"` 응답은 개별 point 영속성 확인서가 아니다.

### Phase 7 — LLM link가 아닌 entity 기반 연결

Phase 7은 LLM이 출력한 `linked_memory_ids`를 사용하지 않는다. `records[].text`에서 entity를 새로 추출하여 별도 collection을 갱신한다.

```text
records의 모든 text
  → extract_entities_batch()
  → 같은 normalized entity를 batch 전체에서 병합
  → entity text batch embedding
  → entity collection exact/semantic match
  ├─ 기존 entity: linked_memory_ids에 새 UUID 합집합 update
  └─ 신규 entity: entity point insert
```

#### `global_entities` 구조

```python
{
    "qdrant": ["ORG", "Qdrant", {"main-memory-uuid-1", "..."}],
}
```

normalize key는 entity text의 앞뒤 공백 제거, 소문자화, 연속 공백 축소로 만든다. entity type은 key에 포함하지 않으므로 같은 표면 문자열이 서로 다른 type으로 추출되면 먼저 들어온 type 아래 합쳐진다.

#### 기존 entity 판정

1. scope의 entity를 최대 10,000개 list하여 normalized exact text map을 만든다.
2. 각 새 entity vector로 `search_batch(top_k=1)`한다.
3. exact match가 있으면 우선 사용한다.
4. exact match가 없으면 semantic score `>= 0.95`인 첫 결과를 같은 entity로 본다.

기존 entity이면 payload의 `linked_memory_ids`와 이번 `memory_ids`를 set union하여 update한다. 신규이면 다음 payload로 별도 UUID point를 만든다.

```python
{
    "data": "Qdrant",
    "entity_type": "ORG",
    "linked_memory_ids": ["main-memory-uuid-1"],
    "user_id": "alice",
    "agent_id": "research-agent",
    "run_id": "run-001",
}
```

entity store는 처음 필요할 때 `{main_collection}_entities` 이름으로 lazy 생성된다. Qdrant embedded mode에서는 RocksDB lock 충돌을 피하려 main store client를 공유한다.

#### 실패 처리

- entity batch embedding 실패: entity별 embedding으로 fallback
- embedding 수가 entity 수와 다름: warning 후 자르거나 `None`으로 채움
- 개별 entity embedding 실패: 해당 entity만 제외
- entity update 실패: debug log 후 계속
- 신규 entity batch insert 실패: warning 후 계속. 개별 insert fallback은 없음
- Phase 7 전체 실패: warning 후 Phase 8로 계속

따라서 main memory가 성공하고 entity link만 빠질 수 있다. 반대로 Phase 6에서 실제 insert에 실패한 memory UUID가 entity payload에 들어가는 false link도 가능하다.

#### 두 `linked_memory_ids`는 다른 것이다

| 위치 | 생성 근거 | 현재 동작 |
| --- | --- | --- |
| LLM output의 `linked_memory_ids` | same topic, 변화, 후속 사건, 모순에 대한 모델 판단 | 무시됨 |
| entity payload의 `linked_memory_ids` | 같은 entity 문자열/semantic match | 실제 저장되고 search boost에 사용 |

즉 현재 내장 graph memory는 LLM이 만든 narrative edge가 아니라 `entity → main memory UUID[]` 역색인에 가깝다.

### Phase 8 — recent message 저장과 반환

마지막으로 vision 처리까지 끝난 이번 `messages`를 SQLite에 저장한다.

```python
self.db.save_messages(messages, session_scope)
```

- 모든 message에 한 번 계산한 동일 `created_at`이 들어간다.
- scope별 최근 10개를 제외한 row는 같은 transaction에서 삭제한다.
- memory fact가 하나도 추출되지 않았거나 embedding 뒤 `records`가 비어도 recent messages는 저장한다.
- LLM provider 호출, Phase 1 retrieval처럼 앞 단계에서 예외가 전파되면 이 지점에 도달하지 못해 저장되지 않는다.

반환값은 실제 저장 확인 결과가 아니라 `records`를 그대로 변환한 것이다.

```json
{
  "results": [
    {
      "id": "코드가 생성한 UUID",
      "memory": "추출된 text",
      "event": "ADD"
    }
  ]
}
```

Phase 6 개별 insert 실패는 반환값에서 제거되지 않는다. 반대로 `save_messages()`가 실패하면 Qdrant main memory, history, entity update가 이미 끝났어도 예외가 전파된다. 호출자가 전체 실패로 판단해 같은 요청을 재시도하면 의미 중복이 생길 수 있다.

## 5. 실패 지점별 실제 관찰 결과

| 실패 지점 | 호출자 관찰 | recent messages | 앞선 side effect |
| --- | --- | --- | --- |
| 입력/scope 검증 | 예외 | 없음 | 없음 |
| vision 처리 | 예외 또는 message 제외 | 없음 | 없음 |
| Phase 1 query embedding/search | 예외 | 없음 | 없음 |
| LLM provider 호출 | `LLMError` | 없음 | 없음 |
| JSON syntax/root parse | 빈 results | 저장 | 없음 |
| JSON 내부 schema 오류 | 후속 `.get()` 등에서 예외 가능 | 보장 안 됨 | 보통 없음 |
| 모든 fact embedding 실패 | 빈 results | 저장 | 없음 |
| Qdrant batch 및 일부 개별 insert 실패 | 성공처럼 보이는 ADD 가능 | 저장 | history/entity false reference 가능 |
| SQLite history 실패 | ADD 반환 가능 | 저장 | Qdrant main memory는 존재할 수 있음 |
| entity linking 실패 | ADD 반환 | 저장 | main/history는 존재, entity boost만 빠짐 |
| 마지막 message 저장 실패 | 예외 | 실패 | main/history/entity는 이미 변경됐을 수 있음 |

이 표 때문에 운영 wrapper는 `add()`의 성공/실패를 단순히 HTTP 또는 Python 예외 하나로 해석해서는 안 된다. idempotency key, 실제 point 확인, outbox/reconciliation이 별도 필요하다.

## 6. V3가 사용하는 세 종류의 문맥

서로 목적과 수명이 다르다.

| 문맥 | 출처 | 크기 | 사용 목적 | 장기 보존 |
| --- | --- | --- | --- | --- |
| `Last k Messages` | SQLite messages | 실제 최대 10 rows | 대명사·생략·직전 대화 해석 | 10개 초과 시 삭제 |
| `Existing Memories` | Qdrant dense search | 최대 10 facts | 의미 중복 억제와 link 판단 prompt | main collection에 지속 |
| entity links | entity collection | entity별 UUID 목록 | read 시 관련 main memory boost | 명시 삭제까지 지속 |

`Last k Messages`를 늘리는 것과 기존 memory retrieval `top_k=10`을 늘리는 것은 다른 조정이다. 전자는 대화 해석 범위와 prompt token을 바꾸고, 후자는 LLM이 중복 판단에 참고할 장기 사실 recall을 바꾼다.

## 7. Prompt의 의도와 실제 구현 비교

| 기능 | Prompt/주석이 암시하는 동작 | 현재 OSS snapshot의 실제 동작 |
| --- | --- | --- |
| ADD/UPDATE/DELETE | `add()` docstring 일부에 남아 있음 | V3 자동 path는 ADD-only |
| 최근 메시지 | prompt 설명상 최대 20 | SQLite wiring은 최대 10 |
| recently extracted memories | dedup의 primary reference라고 설명 | builder 호출에서 전달하지 않아 `[]` |
| summary | 사용자 profile summary 활용 | builder 호출에서 전달하지 않아 빈 값 |
| observation date | 실제 대화 시각 | OSS `timestamp` 거부, 실행 당시 date 사용 |
| same-language output | builder가 옵션 제공 | 호출에서 `use_input_language=True`를 넘기지 않음 |
| Existing Memory ID | prompt에는 UUID 형식 | 실제 입력은 `"0"`, `"1"` 임시 ID |
| anti-hallucination mapping | 임시 ID를 안전하게 실제 UUID로 복원할 의도 | `uuid_mapping` 생성 후 미사용 |
| 직접 memory linking | LLM `linked_memory_ids` 저장 | 해당 필드를 무시 |
| entity graph | 관련 memory가 graph로 연결된다고 설명 | entity payload의 main-memory UUID 배열로 boost 구현 |
| strict JSON schema | `response_format=json_object` | 세부 schema validation 없음 |

이 불일치들은 “문서 표현이 조금 다른 정도”가 아니라 Gemma 4 31B PoC와 fork 범위를 정하는 입력이다. Prompt에 기능이 적혀 있다는 이유만으로 실제 side effect가 있다고 판단하면 안 된다.

## 8. Sync와 Async 구현 차이

`AsyncMemory._add_to_vector_store()`도 같은 8단계를 복제한다. blocking LLM, embedding, vector store, SQLite 호출을 주로 `asyncio.to_thread()`로 감싸는 것이 핵심 차이다.

다음 동작은 sync와 async에 공통이다.

- 최근 messages 10개와 기존 dense memory 10개
- 임시 ID와 사용되지 않는 `uuid_mapping`
- LLM `linked_memory_ids` 미사용
- MD5 exact dedup
- batch 실패 후 개별 main insert fallback
- 실제 insert 성공 집합을 추적하지 않는 false-success 가능성
- entity failure를 non-fatal로 처리
- 마지막 recent-message 저장 실패가 전체 호출 예외가 되는 순서

따라서 sync에서 발견한 correctness 문제를 async가 해결한다고 보면 안 된다. 두 경로를 수정할 때도 같은 변경을 각각 반영하고 parity test가 필요하다.

## 9. 우리 시스템에서의 보강 지점

### 9.1 최근 문맥 설정 분리

현재 `10`은 조회와 삭제 정책에 하드코딩돼 있다. 다음처럼 분리하는 편이 낫다.

```python
recent_message_context_limit = 20
message_history_retention_limit = 100
```

retention은 넉넉히 두고 LLM에는 token budget 안의 일부만 전달해야 한다. message 개수만이 아니라 token 또는 문자 budget 기반 trimming도 필요하다.

### 9.2 LLM output schema 검증

`memory`가 list인지, item이 object인지, `text`가 non-empty string인지 검증한 뒤 Phase 3으로 넘긴다. 형식 오류와 “추출할 사실 없음”을 다른 결과/metric으로 기록해야 한다.

### 9.3 직접 linking을 쓸 것인지 명시적으로 결정

LLM narrative link가 필요하다면 다음 순서가 필요하다.

```text
LLM linked temp IDs
  → uuid_mapping allowlist 검증
  → 실제 UUID로 복원
  → main payload 또는 PostgreSQL relation table에 저장
```

LLM link를 쓰지 않을 것이라면 prompt에서 해당 지시와 예시를 제거하여 Gemma가 불필요한 필드를 만들지 않게 하는 편이 낫다. 현재처럼 출력시키고 버리는 상태는 token과 오류 가능성만 늘린다.

### 9.4 persistence 결과를 성공 ID 기준으로 축소

Qdrant 개별 fallback 결과를 수집해 성공한 record만 history, entity, 반환 대상으로 넘겨야 한다. 더 강한 정합성이 필요하면 PostgreSQL outbox에 업무 이벤트를 기록하고 worker가 Qdrant/history store/entity를 갱신한 뒤 reconciliation한다. stock 코드를 분석할 때 history store는 SQLite지만, 우리 운영 fork에서는 PostgreSQL adapter로 대체한다.

### 9.5 한국어와 시간 정책 노출

- `use_input_language=True`를 wrapper 설정으로 노출하거나 custom instructions로 한국어 출력을 강제한다.
- observation date를 caller가 전달할 수 있게 하거나 transcript import 전에 상대 날짜를 절대 날짜로 정규화한다.
- prompt의 “when in doubt, extract”가 우리 precision-first 정책과 맞는지 Gemma 4 31B 평가셋으로 검증한다.

## 10. PoC에서 남겨야 할 관측값

한 번의 `add()`마다 최소 다음 값을 추적한다.

| 구간 | 관측값 |
| --- | --- |
| Phase 0 | recent row 수, 문맥 문자/token 수, 잘린 message 수 |
| Phase 1 | dense top-10 ID/score, 정답 기존 memory 포함 여부 |
| Phase 2 | raw LLM output, JSON parse 상태, schema validation 상태, 추출 수 |
| Phase 3 | batch/개별 fallback 여부, embedding 성공 text 수 |
| Phase 4·5 | MD5 제외 수, 의미 중복 수, 최종 record 수 |
| Phase 6 | main insert 성공 ID, history 성공 ID, 불일치 ID |
| Phase 7 | 추출 entity, exact/semantic match, link 성공/실패 |
| Phase 8 | message 저장 여부, 실제 반환 ID의 `get()` 확인 결과 |

최종 품질 지표는 JSON 성공률만으로 판단하지 않는다. 사실 precision/recall, 의미 중복률, 잘못된 attribution, 시간 해석, 한국어 보존, 실제 Qdrant 존재율을 분리해야 한다.
