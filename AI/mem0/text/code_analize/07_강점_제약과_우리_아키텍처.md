# Mem0의 강점·제약과 우리 아키텍처 적용 기준

> 근거 문서: [01_전체_아키텍처.md](01_전체_아키텍처.md) ~ [06_SQLite_History와_Lifecycle.md](06_SQLite_History와_Lifecycle.md)  
> 기준 snapshot: `mem0ai 2.0.12` (upstream commit 미확인)

## 결론

Mem0를 사용하는 이유는 “Qdrant API를 감싼다”는 한 가지가 아니다. 대화/agent 입력을 사실 메모리로 만들고, 저장·이력·검색·엔티티 기반 boost·선택적 rerank까지를 **일관된 SDK pipeline**으로 제공한다는 데 있다.

다만 Mem0는 장기 기억의 모든 정책을 대신하지 않는다. 원문 보관, 최신성의 권위, 권한, 출처·버전, 업무 트랜잭션은 MinIO·PostgreSQL·LangGraph/MemoryService가 맡아야 한다.

## 1. Qdrant 직접 사용과 Mem0의 차이

| 항목 | Qdrant 직접 사용 | Mem0 Python library mode |
| --- | --- | --- |
| 대화 → 저장 단위 | 애플리케이션이 chunk/fact 분리 직접 구현 | LLM extraction prompt로 `memory[].text` 생성 |
| 중복 처리 | 직접 구현 | 관련 memory 문맥 + MD5 exact dedup |
| 대화 문맥 | 직접 저장/조회 | scope별 최근 10개 메시지를 내부 store에서 추출 prompt에 제공. stock store는 SQLite |
| 검색 | dense/filter API 직접 호출 | semantic + BM25 + entity boost fusion, optional rerank |
| entity 연관 | schema·graph·조회 로직 직접 구현 | 병렬 entity collection과 `linked_memory_ids` 자동 관리 |
| lifecycle history | 직접 구현 | stock SQLite에 ADD/UPDATE/DELETE 내부 이력 제공 |
| provider 전환 | adapter를 직접 작성 | LLM/embedder/vector store/reranker factory 구조 |

즉 Qdrant만으로도 모두 만들 수 있다. Mem0의 가치는 그 기능들의 구현 시간과 일관성 있는 기본값을 줄여 주는 데 있다. 반대로, Mem0 기본값이 우리 도메인과 맞는지 검증하지 않고 그대로 쓰면 정책을 외부 prompt에 맡기는 위험이 생긴다.

## 2. 강점과 실제 구현 근거

| Mem0 강점 | 실제 구현 | 실무 효과 |
| --- | --- | --- |
| 사실 단위 대화 기억 | `ADDITIVE_EXTRACTION_PROMPT` + `add(infer=True)`의 LLM 1회 JSON 추출 | raw transcript 대신 독립적으로 읽히는 fact 저장 |
| 저장 throughput | extracted facts의 `embed_batch` 및 Qdrant batch `insert` | 여러 fact를 한 turn에서 효율적으로 기록 |
| 검색 신호 다변화 | dense semantic, Qdrant BM25 sparse, entity boost의 `score_and_rank` | 고유명사/키워드/연관 엔티티를 의미 유사도만으로 놓치는 문제 완화 |
| graceful degradation | spaCy/fastembed/keyword search 실패 시 semantic-only로 계속 동작 | optional dependency 장애가 전체 검색 장애로 번지는 것을 줄임. 단 spaCy model 자동 download 시도는 운영 제어 필요 |
| 내장 entity linking | `{collection}_entities` payload의 `linked_memory_ids` | graph DB 없이 entity 중심 recall boost |
| lifecycle API | update/delete + history store + entity cleanup | 명시적 수정·삭제와 내부 변경 추적. stock store는 SQLite |
| sync/async API parity | `Memory`와 `AsyncMemory`가 같은 pipeline을 공유 | FastAPI/worker에도 같은 data model 적용 |

## 3. 반드시 이해할 제약

### 3.1 fact 선택은 LLM prompt 중심이다

Mem0는 “행동을 바꿀 만큼 중요한 사실”을 알고 있지 않다. 기본 prompt는 오히려 “의미 있는 내용을 넓게 모두 추출”하도록 지시한다. `custom_instructions`도 모델이 따르도록 유도하는 prompt일 뿐, 강제 validator나 정책 엔진이 아니다.

**우리 대응:** LangGraph에서 저장 전 조건을 만들고 MemoryService가 memory kind, source, confidence, ownership을 확인한 뒤 `add()`를 호출한다.

### 3.2 V3 ADD-only는 최신 상태를 자동 보장하지 않는다

자동 add는 새 사실을 누적한다. MD5는 정확히 같은 문자열만 막고, 유사 표현·모순·만료된 사실을 해소하지 않는다.

**우리 대응:** 현재 상태는 PostgreSQL에 versioned record로 두고, 변경 사항은 명시적 `Mem0.update()`/`delete()` 또는 superseded metadata 정책으로 관리한다. superseded metadata는 자동 반영되지 않으므로 search filter/query 정책에도 명시적으로 포함한다.

### 3.3 hybrid는 semantic candidate에 종속된다

BM25/entity 결과는 후보군을 확장하지 않는다. threshold도 semantic 점수에 먼저 적용된다.

이것은 Qdrant 자체의 한계가 아니다. Qdrant는 dense/sparse 후보를 `prefetch`하고 RRF/DBSF로 결합할 수 있지만, Mem0의 Qdrant adapter는 이 native fusion을 사용하지 않는다. Mem0는 여러 vector store에서 동일한 중앙 scoring과 entity boost를 적용하는 대신 sparse-only recall을 포기한 구조다. provider 중립성·entity 결합·graceful degradation은 코드에서 추론할 수 있는 이유이며, 개발자가 Qdrant Native Hybrid를 배제한 이유를 직접 밝힌 자료는 확인되지 않았다.

**우리 대응:** dense embedding 모델, top-k over-fetch, threshold를 한국어 query로 측정한다. 동시에 Mem0 기본 검색과 Qdrant Native dense∪sparse fusion의 Recall@K·MRR·latency를 비교한다. keyword retrieval이 핵심인 원문 RAG는 별도 retrieval 설계를 두며, Mem0 검색을 확장할 경우 native fusion 뒤 entity boost와 reranker를 적용하는 MemoryService/fork 경계를 사용한다.

### 3.4 한국어 NLP 보조 기능은 기본적으로 약하다

이 snapshot의 lemma/entity 유틸은 `en_core_web_sm`을 로드한다. Gemma 4의 한국어 추출 능력과는 별개로, BM25 lemma와 entity boost는 영어 모델 의존성이 있다.

**우리 대응:** 한국어 memory benchmark에서 semantic-only와 hybrid를 직접 비교한다. hybrid 품질이 나쁘면 entity boost/BM25는 비활성화하거나 한국어에 맞는 별도 검색 계층을 검토한다.

### 3.5 Qdrant/history store 분산 정합성은 제공되지 않는다

Qdrant point, history/message store, entity collection 변경은 하나의 트랜잭션이 아니다. stock 구현에서는 그 store가 SQLite다. PostgreSQL adapter로 교체하면 중앙 공유·백업·삭제 정책은 좋아지지만 Qdrant와 PostgreSQL 사이의 dual-write 원자성까지 해결되지는 않는다.

**우리 대응:** SQLite는 알고리즘 필수가 아니므로 운영에서는 PostgreSQL adapter로 대체한다. 그 위에 PostgreSQL outbox와 worker retry를 두어 업무 단위 처리 결과를 기록하고 reconciliation할 수 있게 한다.

### 3.6 filter는 접근 제어가 아니다

scope filter는 중요하지만 wildcard와 text operator의 실제 의미가 vector store에 따라 달라질 수 있다.

**우리 대응:** 인증/인가와 tenant isolation은 API/PostgreSQL에서 먼저 강제한다. Mem0 filter는 추가적인 retrieval narrowing으로 사용한다.

### 3.7 API 성공 응답과 전체 영속 성공은 같지 않다

V3 개별 insert fallback 실패가 반환 결과에서 제거되지 않고, async `delete_all()`도 부분 실패 후 성공 message를 반환할 수 있다. Qdrant `list()` pagination 부재로 scope memory가 100개를 넘으면 `delete_all()`이 일부만 지울 수도 있다.

**우리 대응:** MemoryService는 add 반환 ID를 read-after-write로 확인하고, 삭제 후 scope count를 검증한다. 실패·재시도·reconciliation 상태는 PostgreSQL에 기록한다.

### 3.8 삭제와 privacy lifecycle이 완결되지 않는다

stock SDK에서는 memory point를 지워도 SQLite history에 이전 text가 남고 recent messages도 삭제되지 않는다. `reset()`만 전체 SQLite를 비운다.

**우리 대응:** 운영용 PostgreSQL adapter에 scope별 삭제, 보존 기간, tenant 조건과 audit 정책을 구현한다. Mem0 stock SQLite의 동작을 규제상 삭제 원장으로 그대로 복제하지 않는다.

### 3.9 prompt 기능과 실제 저장 계약에 차이가 있다

prompt가 요구하는 `linked_memory_ids`는 V3 write path에서 무시되고, 같은 입력 언어 출력 옵션도 기본 호출에서 켜지지 않는다. JSON Schema 검증도 없다.

**우리 대응:** 한국어 지침과 schema validator를 MemoryService에 추가하고, direct narrative link가 필요하면 PostgreSQL relation 또는 별도 구현으로 보완한다.

## 4. 확정한 구성의 역할 경계

```text
사용자 / Research Agent
          │
          ▼
LangGraph + DeepAgents
  - 작업 순서, tool 호출, 승인, 재시도, 상태 전이
          │
          ▼
MemoryService
  - 저장 승격 기준, current/supersede 정책, outbox, 관측성
     ├──────► MinIO
     │         원문 PDF/HTML, 수집 artifact, 첨부, 재현 근거
     ├──────► PostgreSQL
     │         job/문서/요약/버전/ACL/source mapping/감사/현재 상태
     │         + Mem0 history/recent-message store
     └──────► Mem0 + Qdrant
               durable fact, 사용자·agent 정책, 결정, 선호의 recall
```

### 저장 기준 예시

| 산출물 | 주 저장소 | Mem0에도 저장할 조건 |
| --- | --- | --- |
| 수집한 원문 | MinIO | 저장하지 않음 |
| 긴 조사 보고서 | MinIO + PostgreSQL | 결론 중 반복 사용될 확정 결정만 fact로 |
| 문서 요약 | PostgreSQL | agent 행동을 바꾸는 핵심 제약/정책이면 fact로 |
| 사용자 선호 | Mem0 + Qdrant | 원칙적으로 저장 대상 |
| 도구의 일시적 출력 | run state 또는 PostgreSQL | 보통 저장하지 않음 |
| 출처 불명/불확실 가설 | PostgreSQL에 상태와 출처 | 확정 전에는 Mem0 저장 금지 |

## 5. MemoryService의 최소 정책

Mem0 호출 앞에 다음 같은 작은 정책 계층을 둔다.

```text
should_promote(result):
  1. 원문/장문 chunk/일시적 tool output인가? → 아니오
  2. 이후 agent의 판단·행동에 재사용되는 사실/정책/결정인가? → 예면 후보
  3. research-derived인가? → source_id·version·confidence 필수
     user-stated인가? → run_id/message_id 등 대화 provenance 연결
  4. PostgreSQL current state와 모순되는가? → update/supersede flow
  5. scope와 metadata가 완전한가? → Mem0.add/update 호출
  6. 반환 ID가 실제 조회되는가? → 확인 후 promotion 완료 처리
```

이 정책은 처음부터 거대한 알고리즘일 필요가 없다. 명시적인 rule + 관측 가능한 로그 + PoC 평가셋으로 시작해 운영 사례를 반영하며 확장하는 편이 안전하다.
