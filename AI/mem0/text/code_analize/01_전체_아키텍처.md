# Mem0 Python Library Mode 전체 아키텍처

> 분석 대상: `AI/mem0/code/mem0_code_analize/mem0`  
> 기준 snapshot: `mem0ai 2.0.12` (upstream commit 미확인, 상세 provenance는 [00_분석_계획.md](00_분석_계획.md))  
> 범위: Python OSS **library mode**. `server/`, `mem0/client/`, `mem0-ts/`는 실행 경로 분석에서 제외한다.

## 결론

Python library mode에서 Mem0는 독립 서버가 아니라, 애플리케이션 프로세스 안에서 동작하는 **메모리 오케스트레이션 라이브러리**다. stock `Memory` 객체가 LLM, 임베딩 모델, 벡터 저장소, SQLite를 조립하고 다음 두 흐름을 제공한다. 다만 "in-process"는 "모두 로컬"이라는 뜻이 아니다. 설정에 따라 LLM·embedder·Qdrant는 외부 API/서비스를 호출한다.

```text
애플리케이션
  │
  ├─ Memory.add(messages, ...)
  │    └─ LLM 사실 추출 → 임베딩 → Qdrant 저장 → SQLite 이력/최근 대화 → 엔티티 연결
  │
  └─ Memory.search(query, filters, ...)
       └─ 임베딩 의미 검색 + BM25 + 엔티티 boost [+ 선택적 reranker] → 결과 반환
```

따라서 Qdrant는 Mem0의 한 구성 요소일 뿐이다. Qdrant가 벡터와 payload를 저장·검색한다면, Mem0는 대화 입력을 장기 메모리 단위로 바꾸고 여러 검색 신호를 결합하며 이력과 세션 문맥을 관리한다.

## 1. 진입점과 객체 구성

### 핵심 클래스

| 역할 | 실제 코드 |
| --- | --- |
| 동기 SDK | `mem0/memory/main.py`의 `Memory` |
| 비동기 SDK | 같은 파일의 `AsyncMemory` |
| 설정 모델 | `mem0/configs/base.py`의 `MemoryConfig` |
| 기본 로컬 이력 저장소 | `mem0/memory/storage.py`의 `SQLiteManager` |
| Qdrant 구현체 | `mem0/vector_stores/qdrant.py`의 `Qdrant` |

`Memory.from_config(dict)`는 입력 dict를 `MemoryConfig`로 검증한 뒤 `Memory`를 생성한다. `AsyncMemory`도 같은 설정 구조를 사용한다.

### `Memory.__init__()`가 만드는 컴포넌트

`Memory.__init__()`은 팩토리로 다음 객체를 생성한다.

| 필드 | 생성 방식 | 책임 |
| --- | --- | --- |
| `embedding_model` | `EmbedderFactory.create(...)` | 입력/메모리 텍스트를 dense vector로 변환 |
| `vector_store` | `VectorStoreFactory.create(...)` | Qdrant 등 벡터 저장소에 insert/search/update/delete 위임 |
| `llm` | `LlmFactory.create(...)` | `add(infer=True)`의 사실 추출 응답 생성 |
| `db` | `SQLiteManager(history_db_path)` | 메모리 변경 이력과 최근 메시지 보관 |
| `reranker` | 설정된 경우만 `RerankerFactory.create(...)` | 검색 결과의 선택적 재정렬 |
| `entity_store` | 처음 필요할 때 지연 생성 | 엔티티와 메모리 ID 연결을 별도 collection에 저장 |

기본 SQLite 경로는 `MemoryConfig.history_db_path`의 `~/.mem0/history.db`다. 즉, Qdrant만 외부로 지정해도 이력 DB는 별도 설정하지 않으면 로컬 사용자 홈에 생성된다. 여기에는 vector store와 달리 provider factory가 없고 생성자와 `reset()`이 `SQLiteManager`를 직접 생성한다. 따라서 현재 SDK 설정만으로 PostgreSQL history/message store를 선택할 수 없으며, 우리 운영 구성에서는 이 작은 storage 경계를 adapter/fork로 만들어 PostgreSQL로 대체한다. 상세 근거와 필요한 메서드는 [06_SQLite_History와_Lifecycle.md](06_SQLite_History와_Lifecycle.md)에 정리했다.

### 생략하면 적용되는 기본값

| component | 기본값 | 운영상 의미 |
| --- | --- | --- |
| LLM | `openai` | API key와 외부 호출이 필요할 수 있음 |
| embedder | `openai` | 임베딩도 별도 외부 호출이 될 수 있음 |
| vector store | `qdrant` | config가 없으면 로컬 `path=/tmp/qdrant`를 채움 |
| history | `~/.mem0/history.db` | pod/worker마다 다른 로컬 파일이 될 수 있음 |
| telemetry | `MEM0_TELEMETRY=True` | 기본적으로 익명 PostHog event 전송 코드가 활성화됨 |

폐쇄망·민감 데이터 환경에서는 provider 설정을 모두 명시하고, 외부 telemetry가 허용되지 않으면 **Mem0 import/초기화 전에** `MEM0_TELEMETRY=false`를 설정한다. telemetry event에는 memory 본문 대신 collection, provider class, vector size, filter key와 scope ID의 MD5 등이 실리지만, 네트워크 송신 자체가 정책 대상이다. 또한 telemetry가 켜져 있으면 초기화 중 `mem0migrations`라는 보조 collection을 만들 수 있다.

## 2. 저장소별 실제 책임

```text
                         ┌────────────────────────────────┐
messages ──► LLM ──►    │ main memory collection           │
                         │ dense vector + payload          │
query ───► Embedder ──►  │ (Qdrant 등 vector_store)        │
                         └──────────────┬─────────────────┘
                                        │
                         ┌──────────────▼─────────────────┐
                         │ {collection}_entities           │
                         │ entity text ↔ linked_memory_ids │
                         └────────────────────────────────┘

                         ┌────────────────────────────────┐
                         │ history/message store           │
                         │ stock: SQLite / 우리 운영: PG   │
                         └────────────────────────────────┘
```

| 저장 위치 | Mem0 코드상 데이터 | 목적 |
| --- | --- | --- |
| 주 메모리 collection | `data`, `hash`, `text_lemmatized`, 생성/수정 시각, scope ID, 사용자 metadata | 사실 메모리의 dense/BM25 검색 |
| 엔티티 collection | `data`(엔티티 문자열), `entity_type`, `linked_memory_ids`, scope ID | 같은 엔티티를 공유하는 메모리에 검색 boost 부여 |
| history store의 `history` | ADD/UPDATE/DELETE 이벤트, 이전/새 텍스트, 시각, actor/role | 내부 변경 이력·디버깅 보조. stock 구현은 SQLite, 우리 운영 목표는 PostgreSQL adapter |
| history store의 `messages` | `session_scope`, role, content, name, 시각 | 다음 `add()` 시 지시어·대명사 해석을 위한 직전 대화. stock 구현은 SQLite, 우리 운영 목표는 PostgreSQL adapter |

엔티티 collection 명칭은 `Memory.entity_store`에서 `_entity_collection_name(...)`으로 만들며, Qdrant embedded mode에서는 RocksDB 잠금 충돌을 피하기 위해 기존 Qdrant client를 공유한다.

## 3. API에서 내부 흐름으로

| 공개 API | 내부 핵심 경로 | 결과 |
| --- | --- | --- |
| `Memory.add()` | `_build_filters_and_metadata` → vision parsing(선택) → `_add_to_vector_store()` | 사실 메모리 생성 또는 `infer=False` 원문 메시지 저장 |
| `Memory.search()` | `_search_vector_store()` → reranker(선택) | scope/filter에 맞는 메모리 목록 |
| `get()`, `get_all()` | `vector_store.get/list()` | 저장된 메모리 조회 |
| `update()`, `delete()`, `delete_all()` | vector store 변경 + SQLite history 기록 | 명시적 lifecycle 관리. 다중 저장소 원자성과 Qdrant 전체 pagination은 별도 확인 필요 |
| `history()` | `SQLiteManager.get_history()` | 특정 메모리의 변경 이력 |

`add()`는 `user_id`, `agent_id`, `run_id`로 scope를 만들고 이 값을 payload에도 넣는다. 반면 `search()`와 `get_all()`은 entity ID를 최상위 인자가 아니라 `filters` 안에서 받도록 구현되어 있다.

## 4. Qdrant 사용 시의 계층

`Qdrant` 어댑터는 collection 생성부터 Qdrant API 호출까지 담당한다.

1. `create_col()`은 dense vector와 이름이 `bm25`인 sparse vector slot을 함께 생성한다.
2. `insert()`는 dense vector와, 가능하다면 `text_lemmatized` 기반 BM25 sparse vector를 함께 upsert한다.
3. `search()`는 dense vector로 `query_points()`를 호출한다.
4. `keyword_search()`는 `fastembed`가 있을 때 `bm25` sparse vector로 검색한다.
5. `main.py`가 semantic 점수, BM25 점수, entity boost를 합쳐 최종 순위를 만든다.

즉 Qdrant는 검색 신호를 제공하지만, 어떤 신호를 쓸지와 최종 점수 결합은 Mem0 상위 계층의 책임이다.

## 5. 우리 아키텍처에 적용할 경계

현재 결정한 조합에서 Mem0는 다음 위치에 둔다.

```text
LangGraph / DeepAgent
  └─ MemoryService (저장 승격·삭제·현재성 정책)
       ├─ Mem0 + Qdrant: 재사용할 durable fact / 선호 / 정책 / 결정의 recall
       ├─ PostgreSQL: 문서·조사 결과의 현재 상태, 요약, 버전, ACL, 감사 기준
       │              + Mem0 history/recent-message store(adapter 적용 후)
       └─ MinIO: 원문, 첨부파일, 근거 artifact
```

중요한 경계는 다음과 같다.

- Mem0의 기본 추출기는 대화에서 기억 후보를 만드는 기능이다. **무엇을 장기 기억으로 승격할지**는 우리 `MemoryService`와 LangGraph workflow가 결정해야 한다.
- 조사 원문·긴 보고서 전체는 MinIO에, 구조화된 최신 요약과 상태는 PostgreSQL에 둔다. 이를 모두 Mem0에 넣으면 사실 메모리 검색 품질과 삭제/현재성 관리가 나빠진다.
- 문서 본문 semantic retrieval이 필요하면 Mem0 collection과 별도의 RAG collection으로 분리한다.
- 장기 실행 프로세스는 종료 시 `Memory.close()`/`AsyncMemory.close()`를 호출해 history store, provider client, reranker 자원을 정리한다.
