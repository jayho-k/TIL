# Mem0 동작 원리와 운영상 제약

> 조사 기준일: 2026-07-12  
> 확인 기준: Mem0 OSS `main` commit `17836748d7afe0521516c6a73c6a256680f05527`

## 1. Memory의 기본 단위

Mem0는 session archive나 filesystem node를 저장하는 제품이 아니다. 입력 대화에서 독립적으로 재사용할 수 있는 memory text를 뽑아 vector/payload로 저장하고, 이후 질의와 관련된 사실을 다시 찾는다.

```text
conversation / agent output
  -> reusable fact extraction
  -> embedding
  -> Qdrant vector + payload 저장
  -> later query에서 relevant fact recall
```

따라서 첨부 원문과 full transcript는 MinIO에, business lifecycle과 감사 정보는 PostgreSQL에 둔다. Mem0는 그 사이의 fact extraction·retrieval 계층이다.

## 2. V3 자동 ingestion: ADD-only

최신 OSS V3의 자동 경로는 기존 memory를 읽어 중복을 줄이지만, 자동으로 기존 memory를 `UPDATE`하거나 `DELETE`하지 않는다.

```text
같은 user/agent/run scope의 기존 memory top-10 retrieval
  -> LLM 1회 fact extraction
  -> batch embedding
  -> text MD5 exact deduplication
  -> vector batch insert
  -> entity extraction/linking
  -> SQLite history와 recent messages 기록
```

| 상황 | Mem0 기본 행동 | 애플리케이션이 해야 할 일 |
| --- | --- | --- |
| 선호·규칙 정정 | 새 사실이 추가될 수 있음 | 기존 memory를 찾아 `update` 또는 supersede |
| 오래된 규칙 폐기 | 자동 삭제하지 않음 | status/expiration 또는 explicit delete |
| 의미가 비슷한 중복 | 동일 text hash만 차단 | semantic merge·conflict 정책 |

즉 Mem0를 durable evidence journal로 쓰는 것은 적합하지만, current-state projection을 맡기면 안 된다.

## 3. Qdrant adapter의 실제 구조

```text
chat_portal_mem0             # dense vector + named bm25 sparse vector + payload
chat_portal_mem0_entities    # entity text + linked_memory_ids + scope payload
```

- `fastembed`가 있으면 BM25 sparse vector를 사용한다. 없거나 encoding이 실패하면 semantic-only 또는 entity boost 형태로 degrade될 수 있다.
- dense search가 후보 pool을 만들고, BM25/entity는 그 후보의 ranking boost 역할을 한다. keyword/entity만으로 semantic 후보 밖의 memory를 되살리는 기능은 아니다.
- 기본 자동 payload index는 `user_id`, `agent_id`, `run_id`, `actor_id` 중심이다. `tenant_id`, `project_id`, `memory_tier`, `status`는 Qdrant migration에서 직접 index를 생성한다.
- 과거 collection에 `bm25` sparse slot이 없으면 hybrid search가 꺼질 수 있다. 기존 document RAG collection을 재사용하지 말고 Mem0 전용 collection을 만든다.

## 4. SQLite history는 핵심 제약

`Memory`와 `AsyncMemory`는 vector store 설정과 무관하게 `SQLiteManager(history_db_path)`를 생성한다. 기본 경로는 `~/.mem0/history.db`다.

| SQLite 테이블 | 용도 |
| --- | --- |
| `history` | ADD, explicit UPDATE, explicit DELETE의 old/new text와 시각 |
| `messages` | 같은 user/agent/run의 최근 메시지 context |

V3 extraction은 최근 메시지 일부를 extraction prompt에 넣는다. 따라서 history DB는 단순 감사 부가 기능이 아니라 추출 품질에도 관여한다. 현재 설정에는 `history_db_path`만 있고 PostgreSQL history provider는 없다.

로컬 영속 상태를 허용하지 않는다면 다음 중 하나를 PoC 전에 결정해야 한다.

1. `SQLiteManager`를 PostgreSQL history adapter로 바꾸는 fork/extension을 만든다.
2. SQLite persistent volume을 예외로 명시하고 HA 한계를 받아들인다.
3. Mem0를 raw retrieval 중심으로 제한하고 history·curation은 Portal control plane에서 독립 운영한다.
4. 요구사항과 맞지 않으면 Mem0 OSS를 production engine으로 채택하지 않는다.

## 5. Library mode와 self-hosted server mode

| 관점 | Library mode | Self-hosted REST server |
| --- | --- | --- |
| 적합한 시작점 | 단일 backend/worker PoC | 여러 runtime가 공용 memory API를 사용할 때 |
| Qdrant 설정 | 애플리케이션에서 직접 제어 | server 설정 override를 검증해야 함 |
| history/messages | local `history.db` | container volume의 SQLite |
| 테넌트 권한 | Portal 코드에서 강제하기 쉬움 | API key만으로 payload scope 강제 불가 |
| 초기 권고 | 권장 | shared platform 필요성이 입증된 뒤 검토 |

REST server의 인증은 access authentication에 가깝다. memory id를 아는 다른 tenant가 get/update/delete하지 못하도록 ownership check를 MemoryService에서 수행해야 한다.

## 6. 운영 시 실패 경계

| 장애 | 기대 동작 |
| --- | --- |
| Qdrant | recall/add 실패. memory 없이 degraded 실행 또는 재시도 안내 |
| LLM/embedding | background outbox와 retry. 빈 memory로 성공 처리하지 않음 |
| SQLite history | vector·history 불일치 감지 및 repair 경로 필요 |
| MinIO | 근거 없는 durable promotion을 보류 |
| PostgreSQL control plane | direct Mem0 write를 막고 command outbox 재시도 |
