# 하이브리드 검색 — 의미 검색과 정확한 용어 검색을 한 결과로 합치는 과정

> 학습 단계: 6 / 9  
> 조사 기준일: 2026-07-24  
> 목표: Dense·Sparse 검색이 각각 만든 후보를 `prefetch`, RRF·DBSF, reranker로 결합할 때 무엇이 실제로 일어나는지 이해한다.

## 하이브리드 검색은 vector 두 개를 합치는 기능이 아니다

하이브리드 검색은 같은 query를 서로 다른 검색 방식으로 실행한 뒤, **각 방식이 추천한 Point 순위 목록을 하나로 결합**하는 검색 전략이다.

```text
사용자 query
  ├─ dense query → 의미상 가까운 Point 순위
  └─ sparse query → 정확한 단어·식별자가 겹치는 Point 순위
                    ↓
                  fusion
                    ↓
               최종 후보 순위
```

필요한 이유는 dense와 sparse가 놓치는 경우가 다르기 때문이다.

- dense는 “HNSW 인덱스 설정”과 “벡터 검색 그래프 구성”처럼 표현이 달라도 의미가 가까운 결과를 찾기 쉽다.
- sparse는 `QDR-1842`, 특정 함수명, 사람 이름처럼 정확한 token이 중요한 결과를 놓치지 않게 한다.

따라서 hybrid는 둘 중 하나가 항상 더 좋다는 뜻이 아니라, **query와 corpus에서 두 신호가 서로 보완되는지**를 평가하는 선택이다. 짧은 preference/fact memory만 있고 정확 식별자 검색이 거의 없다면 dense 단독이 더 단순하고 충분할 수 있다.

## 1. `prefetch`: 먼저 후보군을 만든 뒤, 그 결과에 main query를 적용한다

Qdrant Query API에서 `prefetch`는 sub-query다. prefetch가 있으면 Qdrant는 먼저 각 prefetch의 후보를 찾고, 그 결과를 대상으로 main query를 적용한다.

```text
prefetch 1: `semantic` dense vector에서 상위 20개
prefetch 2: `lexical` sparse vector에서 상위 20개

main query: RRF fusion
  → 두 상위 목록의 Point를 하나의 순위로 결합
  → 최종 상위 10개 반환
```

`prefetch limit`과 최종 `limit`은 다른 값이다.

- prefetch limit: fusion/rerank에 넘길 **후보 풀 크기**
- main limit: caller에게 최종으로 반환할 **결과 수**

후보를 너무 적게 가져오면 dense 또는 sparse의 좋은 Point가 fusion 전에 잘린다. 너무 크게 가져오면 latency·reranker 비용이 늘어난다. offset을 쓸 때 prefetch limit이 `main limit + offset`보다 작으면 결과가 비어 있을 수 있다는 Qdrant 제약도 있다.

### scope filter는 어느 위치에 들어가야 하는가?

hybrid라고 tenant·status filter가 fusion 뒤에만 붙으면 안 된다. 각 prefetch가 다른 tenant의 Point를 후보로 만들지 않도록, 허용 범위 filter를 dense/sparse 후보 경로에 동일하게 강제하는 설계를 우선 검토한다.

```text
dense prefetch  = dense query + tenant/scope/status filter
sparse prefetch = sparse query + tenant/scope/status filter
                         ↓
                    허용 후보만 fusion
```

## 2. RRF: 서로 다른 점수의 크기를 비교하지 않고 “순위”를 합친다

**RRF(Reciprocal Rank Fusion)**는 각 검색 결과에서 몇 위였는지를 사용한다. dense score `0.82`와 sparse score `12.4`처럼 scale이 다른 숫자를 직접 더하지 않는다.

```text
Dense 순위:  A 1위, B 2위, C 3위
Sparse 순위: B 1위, D 2위, A 5위

RRF 결과:
  B는 두 목록 모두 상위 → 강하게 상승
  A도 두 목록에 있어 상승
  C/D는 한 목록에만 있어 상대적으로 낮음
```

Qdrant의 기본 RRF는 각 목록의 rank를 이용해 점수를 더한다. 같은 Point가 여러 검색 방식에서 상위에 반복해서 나오면 더 높은 최종 점수를 얻는다. 그래서 dense/sparse 점수 분포가 서로 달라 “0.8과 10.0 중 무엇이 큰 신호인가”를 정하기 어려울 때 좋은 출발점이다.

RRF가 항상 맞는 것은 아니다. 특정 memory 종류에서 sparse 신호가 거의 잡음이거나 dense 결과가 훨씬 신뢰할 만하다면, weighting과 golden query 평가가 필요하다.

## 3. DBSF: 점수 분포를 정규화한 뒤 결합한다

**DBSF(Distribution-Based Score Fusion)**는 각 prefetch 결과 안에서 score 분포를 정규화한 뒤 합친다. RRF가 순위만 본다면 DBSF는 “1위와 2위의 score 차이가 아주 큰가?” 같은 점수 분포도 반영하려는 방식이다.

| 방식 | 무엇을 결합하는가 | 출발점으로 적합한 경우 | 주의점 |
| --- | --- | --- | --- |
| RRF | 각 후보의 순위 | dense/sparse처럼 score scale이 다른 검색을 처음 결합할 때 | 1위와 2위의 score 격차를 반영하지 않음 |
| DBSF | 정규화한 score | 각 search leg의 score 분포가 의미 있는 신호일 때 | 결과 분포·outlier 영향을 실제 데이터로 검증해야 함 |

Qdrant 공식 FAQ는 dense와 sparse처럼 점수 scale이 호환되지 않는 경우 RRF를 기본 출발점으로 권하고, golden query set에서 retrieval 품질을 비교하라고 안내한다.

## 4. 다단계 검색과 reranker: 후보 생성과 최종 정밀 판단을 분리한다

fusion까지의 dense/sparse search는 많은 Point 중에서 놓치지 않고 후보를 모으는 **recall 단계**다. 그 뒤 reranker는 query와 candidate text를 함께 더 정교한 모델에 넣어 “이 후보가 정말 질문에 답하는가”를 다시 판단하는 **precision 단계**다.

```text
전체 Point
  → dense/sparse prefetch (각 20~수십 개)
  → RRF 또는 DBSF (후보 통합)
  → reranker (상위 후보를 query와 함께 재평가)
  → LLM에 줄 최종 context
```

reranker는 정확도를 올릴 수 있지만 후보마다 추가 모델 실행이 필요해 latency와 비용이 늘어난다. 따라서 모든 query에 무조건 붙이는 기능이 아니라, high-stakes memory recall 또는 hybrid 결과의 precision이 부족하다는 평가 결과가 있을 때 검토할 대상이다.

Qdrant의 `prefetch`는 fusion뿐 아니라 nested multi-stage query에도 쓰인다. 예를 들어 빠른 sparse/dense 후보 생성 뒤 ColBERT MultiVector를 이용해 rerank하는 구조를 만들 수 있다. 이는 1.5의 MultiVector가 “vector를 여러 개 저장하는 기능”을 넘어, 느리지만 정밀한 후단 matching에 쓰일 수 있음을 보여 준다.

## 5. 공개 사례 — Fieldy가 dense HNSW와 BM25를 함께 사용한 흐름

Fieldy는 개인 대화 transcript를 검색 가능한 memory로 제공하는 제품이다. 공개 고객 사례에 따르면 query가 들어오면 retrieval agent가 Qdrant에서 HNSW dense similarity와 BM25 term matching을 수행하고, RRF로 결과를 합친다. 그 뒤 conversation metadata를 Firestore에서 가져와 context를 조립한 후 사용자에게 결과를 반환한다.

```text
Fieldy 공개 흐름
chat query
  → retrieval agent
  → Qdrant: HNSW dense + BM25
  → RRF fusion
  → Firestore: conversation metadata
  → context assembly
  → user result
```

이 사례가 보여 주는 사실은 다음이다.

- 의미 검색(HNSW dense)과 용어 일치(BM25)를 분리해 수행했다.
- fusion 결과만으로 끝내지 않고, metadata를 더해 사용 가능한 conversation context로 조립했다.

공개되지 않은 내용도 분명하다. Fieldy의 Named Vector schema, prefetch 수, Top-K, RRF weight, reranker 사용 여부, user scope filter는 자료에 없다. 따라서 “Fieldy가 hybrid를 썼으므로 모든 subagent memory도 RRF를 써야 한다”는 결론은 낼 수 없다. 이 사례는 hybrid의 실제 적용 이유를 보여 주는 벤더 발행 자료이며, 성능 주장은 독립 검증 자료가 아니다.

**출처:** Qdrant 고객 사례, [How Fieldy AI Achieved Reliable AI Memory with Qdrant](https://qdrant.tech/blog/case-study-fieldy/) (접근일 2026-07-24)

## 6. subagent memory에 적용할 때의 판단 순서

```text
1. 실제 query에 고유명사·ID·코드·정확한 절차명이 자주 있는가?
   └─ 아니오 → dense 단독 baseline부터 평가
   └─ 예     → sparse leg 추가 후보

2. dense와 sparse를 각각 단독 평가했을 때 서로 다른 관련 Point를 찾는가?
   └─ 아니오 → hybrid의 추가 복잡도 이득이 작을 수 있음
   └─ 예     → RRF를 첫 fusion 후보로 평가

3. fusion 후에도 상위 결과의 정확도가 부족한가?
   └─ 예 → reranker 또는 더 정교한 multi-stage 검색 검토

4. 모든 leg에 tenant/scope/status filter가 강제되는가?
   └─ 아니오 → 품질 평가 전에 격리 경로부터 수정
```

## 이 단계에서 아직 확정하지 않는 것

- dense/sparse embedding 모델과 Named Vector field 이름
- prefetch 후보 수, final Top-K, RRF weight, DBSF 선택
- hybrid를 모든 memory kind에 적용할지, procedure/code memory에만 적용할지
- reranker 모델과 latency budget
- fusion 뒤 importance·최신성·confidence를 어떻게 보정할지

이 값들은 실제 memory 데이터와 labeled/golden query를 만든 뒤, dense-only·sparse-only·RRF·DBSF·reranker 조합을 비교해 결정한다.
