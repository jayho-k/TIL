# 검색 원리와 검색 범위 — “가까운 기억”이 아니라 “허용된 가까운 기억”을 반환하는 과정

> 학습 단계: 5 / 9  
> 조사 기준일: 2026-07-24  
> 목표: Qdrant query에서 vector 유사도, Payload filter, HNSW/exact search, Top-K, score threshold가 어떤 순서와 역할로 memory recall 결과를 만드는지 이해한다.

## 검색 결과는 한 번에 만들어지지 않는다

“질문과 비슷한 memory를 찾아라”는 요청은 실제로 두 질문을 함께 포함한다.

1. **관련성:** 질문과 의미·단어가 가까운 memory는 무엇인가?
2. **허용 범위:** 그 memory를 현재 tenant/user/project/subagent가 읽어도 되는가?

Qdrant의 vector는 첫 질문에 점수를 주고, payload filter는 두 번째 질문에 답한다. filter는 점수를 조금 낮추는 보정이 아니라, 조건에 맞지 않는 Point를 후보에서 제외하는 경계다.

```text
사용자 query
  → query를 vector로 변환
  → payload filter로 “허용 Point 집합”을 정함
  → 그 집합에서 vector 유사도 검색
  → score 순으로 정렬
  → Top-K와 score threshold 적용
  → retrieval agent / LLM에 넣을 context 후보 반환
```

이 순서에서 “가장 점수가 높은 Point”라도 tenant 또는 status filter를 통과하지 못하면 반환되면 안 된다.

## 1. vector 유사도 검색: 숫자 점수는 무엇을 뜻하는가?

query text를 embedding model에 넣으면 query vector가 생긴다. Qdrant는 이 vector와 저장된 Point vector 사이의 distance/similarity를 Collection에 설정된 metric으로 계산해 결과를 score 순으로 정렬한다.

```text
query: “고액 지출 승인 절차”
  → query vector
  → Point A: “5만 달러 초과 시 재무 검토”  score 0.86
  → Point B: “회의실 예약 절차”            score 0.41
```

여기서 `0.86`은 “86% 확률로 참”이나 “모든 Collection에서 항상 같은 품질”을 뜻하지 않는다. embedding model, distance metric, vector type, query와 data 분포가 함께 만든 상대적인 유사도 값이다. 따라서 score threshold를 `0.75`처럼 하나 정해 모든 model·Collection에 그대로 적용하면 안 된다.

### Dense와 sparse의 score는 같은 척도가 아니다

- dense vector는 embedding의 전체 패턴이 가까운지를 비교한다.
- sparse vector는 공통 token feature의 가중치가 얼마나 겹치는지를 비교한다.

두 점수의 숫자 크기는 같은 의미가 아닐 수 있다. 그래서 07단계 hybrid search에서 dense score와 sparse score를 단순히 더하기보다 RRF/DBSF 같은 결합 방식을 검토한다.

## 2. HNSW와 exact search: 빠르게 근처를 찾을지, 전부 비교할지

### 2.1 HNSW — 모든 Point를 비교하지 않는 빠른 탐색

HNSW는 vector들을 이웃 관계 그래프로 연결해 두고, query 때 그래프를 따라 가까운 영역으로 이동하는 근사 최근접 이웃(ANN) 방식이다. 모든 Point와 거리를 계산하지 않으므로 대규모 Collection에서 빠르다. 대신 실제로 가장 가까운 Point를 항상 100% 찾는다는 보장은 없다.

```text
exact search
query → 모든 후보 Point와 비교 → 실제 Top-K

HNSW search
query → 그래프의 일부 경로 탐색 → 매우 빠른 근사 Top-K
```

`hnsw_ef`는 query 때 후보 탐색 폭을 조절하는 값이다. 값을 키우면 더 많은 후보를 살펴 recall(정답이 후보에 포함될 가능성)은 높아질 수 있지만 latency와 CPU 비용도 커진다.

### 2.2 Exact search — 기준선·검증을 위한 전체 비교

Qdrant query의 `exact=true`는 HNSW 근사 탐색 대신 전체 scan으로 exact result를 찾는다. 데이터가 작거나, HNSW parameter를 평가하거나, 중요한 golden query의 정답 기준을 만들 때 유용하다. 큰 Collection의 실시간 agent query에 기본으로 쓰면 오래 걸릴 수 있다.

```text
실습/평가
같은 filter·같은 query를 HNSW와 exact로 실행
  → exact 결과를 기준으로 HNSW가 필요한 memory를 얼마나 놓치는지 비교

운영
대부분 HNSW
  → 지연시간과 recall 목표에 맞게 hnsw_ef 조정
```

따라서 exact search는 “더 좋은 운영 설정”이 아니라 **HNSW의 품질과 trade-off를 측정하는 기준선**에 가깝다.

## 3. Payload filter: 유사도 검색 전에 허용 범위를 제한한다

payload filter는 Point payload의 exact match, range, datetime 등 조건을 이용해 후보 범위를 제한한다. memory recall에서는 보통 다음 세 층을 분리해 생각해야 한다.

```text
1. 보안/소유 경계
   tenant_id = 현재 인증 tenant

2. 업무 scope
   user_id, project_id, agent_id, memory_scope

3. 사용 가능 상태
   status = active
   AND expires_at이 없거나 아직 지나지 않음
```

예를 들어 `tenant_id`와 `status=active`는 점수가 높다는 이유로 우회할 수 없는 조건이고, `project_id`와 `agent_private`는 현재 실행 context에 따라 허용 여부가 달라지는 조건이다.

```text
vector score가 가장 높아도
tenant가 다르거나 status=deleted이면
  → 후보에서 제외

vector score가 두 번째여도
현재 tenant·scope·상태를 모두 만족하면
  → 반환 가능
```

### 왜 payload index가 필요한가?

filter 조건을 빠르게 확인하려면 그 field에 payload index가 필요하다. Qdrant의 payload index는 조건을 만족하는 Point 수를 추정해 query planner가 HNSW 탐색과 payload 기반 전체 비교 중 적절한 전략을 고르는 데도 쓰인다. filter-aware HNSW graph의 추가 edge도 payload index를 먼저 만들었을 때 생성된다.

즉 `tenant_id`처럼 모든 query에 붙는 field는 “보기 좋은 metadata”가 아니라 검색 성능·격리 모두의 입력이다. 반면 `content`처럼 주로 반환만 하는 field에 무조건 keyword index를 만들 필요는 없다.

## 4. Top-K와 score threshold: 반환 개수와 최소 관련성은 다른 제어 장치다

### Top-K (`limit`)

Top-K는 score가 높은 결과를 최대 몇 개 반환할지 정한다.

```text
Top-K = 5
→ 허용 범위 안에서 점수 상위 5개까지만 반환
```

이는 LLM context 길이·reranker 비용·응답 지연시간을 제한하는 장치다. 하지만 Top-K만 쓰면 “관련성이 낮아도 후보가 5개 미만이면 낮은 점수 결과까지 반환”될 수 있다.

### score threshold

score threshold는 최소 관련성 기준보다 낮은 결과를 버린다.

```text
Top-K = 5, threshold = 0.75

scores = 0.91, 0.83, 0.77, 0.61, 0.40
→ 반환 = 0.91, 0.83, 0.77
```

Top-K와 threshold를 함께 쓰면 “최대 몇 개”와 “너무 약한 결과는 제외”를 동시에 제어할 수 있다. 다만 threshold는 embedding model과 metric마다 재평가해야 한다. 충분히 관련 있는 결과가 없는 상황에서 빈 결과를 반환하는 것이, 약한 memory를 LLM에게 사실처럼 주입하는 것보다 안전할 수 있는지도 제품 정책으로 결정해야 한다.

## 5. 공개 사례에서 보는 검색 범위와 retrieval

### 사례 A — Qdrant + LlamaIndex: filter가 같은 query의 반환 결과를 바꾼다

Qdrant의 LlamaIndex multitenancy 예제는 같은 Collection에 여러 library 문서를 저장하고, query에 `metadata.library` exact filter를 붙인다. 같은 “large language models” query라도 `library=qdrant`와 `library=llama-index` filter에 따라 서로 다른 node가 반환된다.

이 사례는 filter가 search 결과의 사후 라벨이 아니라 **후보 집합 자체를 바꾸는 조건**임을 보여 준다. 예제는 모든 query가 해당 library 범위에 제한되는 전제에서 payload index를 만들고 global HNSW를 끄는 설정도 제시한다. 따라서 이 HNSW 설정은 global search가 필요한 subagent memory에 자동으로 적용할 값이 아니다.

### 사례 B — Fieldy: dense HNSW와 BM25를 따로 찾은 뒤 RRF로 결합

Fieldy 공개 사례에서 retrieval agent는 Qdrant에서 HNSW dense similarity와 BM25 term matching을 수행하고 RRF로 결과를 합친다. 이는 “의미가 가까운 transcript”와 “정확한 단어를 포함한 transcript”를 하나의 score로 가정하지 않고 각각 후보로 찾은 실제 제품 흐름이다.

공개 자료는 Fieldy의 Top-K, threshold, HNSW parameter, payload filter를 밝히지 않았다. 따라서 해당 값을 이 설계의 근거로 인용할 수는 없다. hybrid 결합의 원리는 07번에서 자세히 다룬다.

### 사례 C — Qdrant 공식 multitenancy: `group_id` filter가 tenant 후보를 제한

Qdrant 공식 multitenancy 문서는 Point의 `group_id` payload와 query의 같은 `group_id` filter를 함께 사용한다. `is_tenant=true` keyword index는 tenant-filtered query를 전제로 Point 배치와 per-tenant index를 최적화한다.

이 사례는 우리 memory query에서도 “현재 tenant filter는 모든 query의 선택 사항이 아니라 구성 요소”라는 설계 근거가 된다. 단, `group_id`가 tenant/user/project 중 무엇이어야 하는지는 제품의 인증 경계가 결정한다.

## 6. subagent memory retrieval의 후보 정책

아래 흐름은 04·05의 후보 field를 실제 query로 연결한 **후보 정책**이다. 아직 최종 채택안이 아니다.

```text
1. 인증된 요청에서 tenant/user/project/agent context를 서버가 확정
2. tenant_id는 항상 must filter
3. status=active와 만료 조건을 항상 filter
4. memory_scope에 따라 user_shared, 현재 project_shared,
   현재 agent_private만 허용
5. 허용 후보에서 vector search
6. Top-K와 threshold로 LLM에 줄 context 크기·최저 관련성 제한
7. 필요하면 importance·최신성·근거 존재 여부로 후처리
```

이 구조는 score가 높더라도 권한·수명·scope가 맞지 않는 기억을 반환하지 않게 한다. 반대로 filter가 너무 엄격하면 관련 memory를 전혀 찾지 못할 수 있으므로, “빈 결과일 때 어느 범위를 넓힐 수 있는가”도 명시적 정책이 필요하다. tenant 경계는 넓히지 않고, 같은 tenant 안에서 project_shared → user_shared 같은 범위를 언제 추가할지처럼 안전한 확장 규칙을 정해야 한다.

## 이 단계에서 검증할 질문

- 업무별 golden query에서 HNSW와 exact search의 recall 차이는 얼마인가?
- memory 종류별로 적절한 Top-K와 threshold는 같은가?
- 모든 query에 tenant/status filter가 실제 service API에서 강제되는가?
- 만료·superseded Point가 어떤 경로에서도 반환되지 않는가?
- filter 조합이 많을 때 latency와 recall이 어떻게 변하는가?
- 빈 결과일 때 범위를 넓히는 fallback이 tenant isolation을 침해하지 않는가?
