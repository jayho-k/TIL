# 메모리 생명주기와 운영 설계 — 저장한 기억을 언제 믿고, 바꾸고, 지우고, 복구할 것인가

> 학습 단계: 7 / 9  
> 조사 기준일: 2026-07-24  
> 목표: subagent memory가 candidate에서 active로 바뀌고, superseded·expired·deleted가 되는 과정과 Qdrant의 update/delete/snapshot 책임 경계를 이해한다.

## memory는 저장 직후부터 “사실”이 아니다

agent가 추출한 문장은 그럴듯해도 틀릴 수 있고, 한시적으로만 맞을 수 있으며, 나중에 더 새 정보로 대체될 수 있다. 따라서 memory system은 “Qdrant에 Point를 upsert했다”를 “이제 모든 agent가 믿어도 된다”와 같은 뜻으로 두면 안 된다.

```text
원문·tool 결과·사람 수정
  → candidate: 추출했지만 아직 공유/신뢰 정책 미통과
  → active: 현재 recall에 사용 가능
  → superseded: 새 정보가 대체, 기본 recall에서는 제외
  → expired: 시간 유효기간 종료, 기본 recall에서는 제외
  → deleted: 삭제 요청 또는 정책에 따라 더 이상 반환하지 않음
```

상태는 memory가 **무엇인지**(`memory_kind`)가 아니라 **지금 검색해도 되는지**(`status`)를 나타낸다.

---

## 1. 상태 전이는 왜 필요한가?

### candidate → active: 추출과 승인/활성화의 분리

subagent의 중간 추론, 자동 요약, tool 실패 결과를 곧바로 shared memory로 쓰면 오류가 다른 agent의 context에 누적될 수 있다. candidate는 “검색용 후보로는 저장했지만 기본 recall에는 넣지 않는 상태”를 표현하는 선택지다.

```text
research-agent가 “고객은 X 정책을 선호한다”를 추출
  → candidate로 기록
  → 원문 evidence·사람 확인·규칙 검증 통과
  → active + project_shared 또는 user_shared로 승격
```

candidate를 아예 Qdrant에 저장하지 않고 원장 DB에만 둘 수도 있다. 반대로 나중에 검토·중복 탐지를 위해 vector search가 필요하다면 같은 Collection에 두되 모든 일반 query에 `status=active` filter를 강제할 수 있다. 어떤 선택이 맞는지는 candidate 수, 검토 흐름, 검색 비용으로 결정한다.

### active → superseded: 과거를 지우지 않고 현재 recall에서 제외

`superseded`는 “삭제할 정도로 잘못된 기록”이 아니라 새 정보가 기존 내용을 대체한 상태다.

```text
기존: “프로젝트 담당자는 Alice”  → active
변경: “프로젝트 담당자는 Bob”   → 새 Point active
기존: status = superseded, successor/evidence를 원장에 연결
```

과거 기록을 보존하면 왜 현재 값이 바뀌었는지 감사·디버깅할 수 있다. 그러나 일반 recall에서 superseded Point를 제외하지 않으면 Alice와 Bob이 함께 반환되어 LLM이 충돌한 정보를 받는다.

### active → expired: 시간이 지나면 자동으로 덜 믿는다

`expired`는 “한때 맞았지만 유효기간이 끝난 정보”다. 예를 들어 일시적 프로젝트 마감일, 임시 권한, 단기 작업 상태가 여기에 해당할 수 있다. `expires_at` 값을 payload에 저장했다면 query에서 현재 시각과 비교해 제외하거나, lifecycle worker가 status를 expired로 변경해야 한다. 값을 저장만 하면 자동으로 검색에서 사라지지 않는다.

### deleted: 검색 제외와 물리 삭제는 같은 단계가 아닐 수 있다

삭제 요청이 오면 먼저 user-facing recall에서 즉시 제외해야 한다. Qdrant point delete 뒤에는 API로 접근할 수 없고, 내부적으로는 bitmask를 이용한 soft delete 후 Vacuum Optimizer가 나중에 물리 정리를 한다. 즉 API 차원의 삭제와 저장 매체에서의 물리적 제거는 시간상 분리될 수 있다.

원문 evidence, audit log, Qdrant vector를 어느 시점에 각각 지울지는 법적 보존·보안·사용자 삭제 요구에 따라 다르므로, Qdrant delete 하나만으로 전체 데이터 삭제 정책이 완료됐다고 보면 안 된다.

## 2. scope 승격은 상태 변경과 다른 축이다

`status=active`가 되었다고 모든 agent가 읽을 수 있는 것은 아니다. `memory_scope`는 누구에게 공개되는지를 나타낸다.

```text
agent_private candidate
  → agent_private active       # 작성 agent만 사용
  → project_shared active      # 프로젝트 agent들이 사용
  → user_shared active         # 사용자 공통 memory로 사용
```

따라서 “승격”에는 두 결정이 들어갈 수 있다.

1. 이 memory를 현재 신뢰해도 되는가? → `status`
2. 신뢰한다면 누가 읽어도 되는가? → `memory_scope`

두 값을 한 번에 바꾸는 정책도 가능하지만, 각각의 변경 이유·승인자·근거는 원장 event로 남기는 편이 안전하다. Qdrant payload에는 현재 projection만 두고, 상태 변경 이력은 별도 저장소에 보관하는 구조를 우선 검토한다.

## 3. Qdrant update/delete가 보장하는 것과 보장하지 않는 것

| 작업 | Qdrant가 제공하는 동작 | memory system이 추가로 결정할 일 |
| --- | --- | --- |
| 같은 ID upsert | 기존 Point를 새 Point로 교체, 재시도에 유리 | 어떤 변경이 허용되는지, 원장과의 부분 성공 복구 |
| payload set/overwrite | 일부 field 변경 또는 payload 전체 교체 | status/scope 변경의 권한·감사·동시 수정 규칙 |
| conditional update | payload `version` 등 조건이 맞을 때만 update 가능 | 업무 version 정의와 conflict resolution |
| point delete | API에서 즉시 접근 불가, 내부 물리 정리는 나중에 수행 | evidence·백업·cache·원장까지 포함한 삭제 절차 |
| snapshot | 특정 시점 Collection 데이터·설정 archive | 여러 node snapshot, 원장 DB 백업, restore priority 검증 |

### 동시 수정: 마지막 write가 조용히 덮어쓰지 않게 하기

두 worker가 같은 memory를 읽고 서로 다른 status/scope로 갱신하면 늦게 도착한 write가 앞선 변경을 덮을 수 있다. Qdrant 공식 Points 문서는 payload의 application-managed `version` 또는 단조 증가 timestamp를 조건으로 둔 conditional update로 optimistic concurrency control을 구현할 수 있다고 설명한다.

```text
worker A가 version=4를 읽음
worker B가 version=4를 읽음

A: “version이 4이면 active로” → 성공, version=5
B: “version이 4이면 expired로” → 실패
    → 최신 원장/Point를 다시 읽고 충돌 정책 적용
```

Qdrant Query API의 내부 Point `version`은 application write 횟수의 신뢰할 수 있는 기준이 아니므로, lifecycle 제어에는 별도 payload version 또는 원장 version을 써야 한다.

## 4. Qdrant와 원장의 부분 성공을 어떻게 볼 것인가?

Qdrant와 PostgreSQL 같은 원장 DB 사이에는 일반적으로 하나의 ACID transaction이 없다. 예를 들어 다음 두 단계 중 하나만 성공할 수 있다.

```text
원장: memory status=active로 변경  → 성공
Qdrant: active Point upsert         → 실패
```

이때 원장은 active인데 retrieval에는 보이지 않는 불일치가 생긴다. 반대 순서면 retrieval에 보이지만 원장 evidence가 없는 memory가 생길 수 있다.

후보 복구 방식은 outbox/작업 큐에 변경 event를 남기고, 안정적인 `memory_id`로 Qdrant upsert를 재시도하는 것이다. Qdrant의 same-ID upsert idempotence는 이 재시도를 돕지만, “어느 상태가 source of truth인가”와 보상 규칙은 애플리케이션이 정해야 한다.

```text
원장 transaction
  → memory_state + outbox event 기록
  → worker가 event를 읽어 Qdrant projection upsert/delete
  → 성공 여부 기록, 실패 시 같은 memory_id로 재시도
```

이 흐름은 설계 보조 예시이며, 현재 프로젝트의 구현 결정은 아니다.

## 5. Snapshot·복구·복제: 검색 DB 복구와 memory system 복구는 다르다

Qdrant Collection snapshot은 해당 Collection의 data, payload, configuration을 담은 archive다. distributed cluster에서는 node별 snapshot이 필요하고, Collection alias는 포함되지 않는다. snapshot restore에는 기존 데이터와 snapshot 중 무엇을 우선할지 priority도 있다.

따라서 “Qdrant snapshot이 있으니 memory system 복구가 끝났다”는 결론은 성립하지 않는다.

```text
Qdrant snapshot이 복구하는 것
  → vector, payload, Collection 설정

별도 복구가 필요한 것
  → 원문 evidence, 상태 전이 audit, 권한 데이터,
     outbox 처리 상태, alias/서비스 설정
```

고가용성이 필요하면 shard replication과 read/write consistency도 따로 결정해야 한다. Qdrant는 기본적으로 가용성과 search throughput을 우선하며, 동시 Point update가 replica 간 일시적으로 다를 수 있는 상황에 대한 consistency 설정을 제공한다. 이는 “정확한 lifecycle 전이가 반드시 즉시 하나의 값으로 보여야 하는가”라는 업무 요구와 함께 결정해야 한다.

## 6. 공개 자료에서 확인되는 운영 사실

### Qdrant 공식 문서

- delete는 즉시 API 접근을 막지만 내부적으로 soft delete 후 background vacuum이 물리 정리를 한다.
- conditional update와 user-managed version은 stale write 방지에 사용할 수 있다.
- snapshot은 Collection의 data·payload·configuration을 담지만 distributed setup에서는 node별 생성이 필요하고 alias는 별도다.
- cluster replication은 가용성을 높이지만, distributed point update의 consistency 수준은 별도 설정·정책이 필요하다.

### Fieldy 사례의 한계가 주는 교훈

Fieldy는 수집 누락이 나중에 복원될 수 없다는 점 때문에 ingestion reliability를 핵심 제약으로 다루고, transcript/embedding 저장과 검색 안정성을 강조했다. 그러나 candidate 승인, memory supersede, 삭제·감사 정책은 공개하지 않았다. 따라서 “신뢰할 수 있는 수집”과 “신뢰할 수 있는 memory lifecycle”은 서로 연결되지만 별도의 설계 문제다.

## 이 단계에서 확정해야 할 질문

- 어떤 memory_kind는 candidate 검토를 거치고, 어떤 것은 즉시 active가 되는가?
- agent_private에서 project/user shared로 승격할 권한은 누구에게 있는가?
- superseded memory를 원장에는 얼마나 오래 보존하는가?
- 사용자 삭제 요청 시 vector·payload·원문 evidence·backup을 각각 어떤 SLA로 처리하는가?
- 원장→Qdrant projection 실패를 어떻게 감지·재시도·감사하는가?
- snapshot restore 뒤 원장과 Qdrant의 version을 어떻게 reconcile하는가?
