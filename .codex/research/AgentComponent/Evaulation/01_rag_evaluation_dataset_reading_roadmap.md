# RAG 평가셋 구축: 후속 논문과 설계 아이디어

> **추천 수정:** 이 문서는 기존 골든셋 약 50개를 보유했다는 전제 없이 작성한 범용 조사다. 사용자의 실제 목적은 해당 골든셋을 기반으로 한 평가셋 확장이므로, 추천 우선순위와 적용안은 [02_seed_golden_set_expansion_research.md](02_seed_golden_set_expansion_research.md)를 따른다. 아래 내용은 초기 조사 이력으로 보존한다.

> 조사 기준일: 2026-10-18. 저자 논문·학회 공식 페이지·도구 공식 문서·저자 기술 보고서를 확인했다. 검색으로 확인한 연구 방향의 정성적 종합이며, 산업 전체의 도입률을 조사한 자료는 아니다. 논문 결과, 해석, 제안 수량을 구분한다. 기존 `Evaulation` 경로 표기를 유지한다.

## 먼저 읽을 논문

**다음 한 편은 [Can we Evaluate RAGs with Synthetic Data?](https://arxiv.org/html/2508.11758v2)를 추천한다.** 평가셋 생성법을 도입하기 전에, 생성한 평가셋으로 내리는 의사결정이 믿을 만한지 검토하기에 가장 직접적이다.

최근 읽은 [검색자 선호 예측 논문](paper/Large_Language_Models_can_Accurately_Predict_Searcher_Preferences_ko_translation.md)은 실제 검색자의 골드 피드백으로 LLM 라벨러를 선택하고 검증하는 접근이다. 여기서 다음 세 문제를 구분해야 한다.

1. 질문이 실제 사용자의 정보 요구를 대표하는가?
2. 질문·문서 관련성 라벨과 정답·근거가 정확한가?
3. 그 평가셋과 채점기로 고른 시스템이 실제 사용자에게도 더 좋은가?

기존 논문의 중심은 관련성 라벨이다. RAG에는 생성 답변의 정확성·근거 충실성·정보의 완전성까지 추가된다. 검색 관련성 라벨의 신뢰도를 그대로 종단간 답변 평가의 신뢰도로 확장할 수는 없다.

### 1. 합성 평가셋의 순위를 사람 평가셋과 비교한다

[논문 본문](https://arxiv.org/html/2508.11758v2)의 §4.5–4.6, §5.2–5.3, §6.2를 우선 읽는다. 공개·비공개 각 2개 데이터셋에서 검색 설정 변경과 생성 모델 변경을 나눠 비교한다. 전자에서는 순위가 비교적 일치했지만 후자에서는 일관되지 않았다. 소수 설정, 단순 생성법과 작은 도메인별 사람 표본이라는 제약이 있어, 모든 합성 방식이나 모든 retriever에 대한 결론은 아니다. **우리에게 주는 시사점:** 합성셋의 크기보다 사람 기준과의 순위 일치를 먼저 검증한다. 근거 강도: 해당 실험 내 중간, 일반화 제한.

### 2. 다양한 질문과 대표적인 질문은 다르다

[Chroma 보고서](https://www.trychroma.com/research/generative-benchmarking)는 업무 맥락과 질문 예시로 생성을 유도하고, 실제 운영 질문의 검색 성능과 비교한다. 문서 선택과 질문 유형 가중치도 다룬다. 동료 심사 논문이 아닌 공급사 기술 보고서이며, 특정 서비스의 관찰이다. **시사점:** 문서마다 같은 수의 질문을 만드는 대신 실제로 물어볼 업무와 빈도를 반영한다. 근거 강도: 중간, 다른 도메인 재검증 필요.

### 3. 합성 데이터로 평가자를 학습해도 사람 기준은 남는다

[ARES](https://aclanthology.org/2024.naacl-long.20/)는 합성 데이터로 경량 평가자를 학습하고, 사람 라벨을 이용한 prediction-powered inference로 추정 오류를 보정한다. context relevance, answer faithfulness, answer relevance를 나눠 평가한다. **주의:** 평가자 학습용 합성 데이터와 시스템을 시험할 최종 평가셋은 역할이 다르다. PPI는 임의 표본의 단순 점수 보정과 동의어가 아니므로 표본 추출·추정 조건을 따라야 한다. 근거 강도: 학회 논문의 해당 실험에서 높음, 한국어·사내 도메인 전이는 미확인.

### 4. 질문·답·근거를 함께 생성하고 교란한다

[RARE v3](https://arxiv.org/html/2506.00789v3)는 문서에서 근거 문장과 관계를 추출하고 그래프 경로를 이용해 단일/다중 홉 QA를 만든다. 질문과 문서 변형에 대한 강건성도 다룬다. 평가용 그래프를 쓴다고 실제 RAG에 GraphRAG를 도입해야 하는 것은 아니다. 자동 생성이 실제 사용자 대표성을 보장하지도 않는다. v3는 527개 문서·48,295개 질문으로, 초기 검색 결과의 수치와 다르다. 근거 강도: 공개 프리프린트의 방법·실험에 대해 중간, 학회 채택 여부는 본 조사에서 확정하지 않음.

### 5. 검색하지 않아도 맞히는 문제를 진단한다

[SeedRG 논문](https://arxiv.org/html/2605.08838v1)은 기존 QA의 추론 그래프를 유지하며 엔터티를 치환하고, 그래프 일관성과 검색 없는 정답 가능성을 검사한다. 해당 모델 집합에 대한 검사이지 모든 모델의 누출 부재를 증명하지 않는다. 합성 세계를 실제 사내 문서의 정답 기준과 섞으면 해석이 어려워진다. **시사점:** 운영 평가셋은 유지하고, 검색 의존성을 확인하는 별도 진단셋을 만든다. 근거 강도: 2026년 프리프린트의 초기 근거, 독립 재현 미확인.

## 2025–2026 연구에서 관찰한 평가셋 생성 방향

### 실제 업무의 분포를 반영하는 생성이 필요하다

문서 기반 QA 생성의 자연스러운 문장만으로는 운영 대표성이 성립하지 않는다. Chroma는 대표성을 생성 목표로 삼고, 첫 번째 추천 논문은 사람/합성셋 사이의 불일치를 실험한다. 서로 모순이라기보다 생성 절차와 검증 대상이 다르다. 우리에게 필요한 것은 **맥락을 반영한 생성 → 별도 실제 질문으로 검증**하는 과정이다. 이는 위 자료들의 종합 해석이며 보편적 성능 보장은 아니다.

### QA 쌍에 근거와 시나리오를 붙이는 방식이 구체화되고 있다

RARE는 연결 근거를, [Ragas v0.4.0 공식 생성 문서](https://docs.ragas.io/en/v0.4.0/getstarted/rag_testset_generation/)는 knowledge graph와 변환을 이용하는 생성을 보여준다. 도구 기능이 있다는 사실과 생성셋의 품질이 입증됐다는 사실은 구분해야 한다. 실무 적용 시 원문 근거를 저장하면 오류가 질문 생성·검색·답변 생성 중 어디서 발생했는지 확인할 수 있다.

### 정답이 없는 질문과 여러 자료를 잇는 업무를 포함한다

[Benchmarking Deep Search over Heterogeneous Enterprise Data](https://aclanthology.org/2025.emnlp-industry.34/) — EMNLP Industry 2025, 2025-11 — 는 업무 흐름을 모사한 합성 문서·메시지 등과 답변 가능/불가능 질문을 구성한다. 단일 문서의 사실 추출을 넘어선 기업 검색 평가 사례다. 합성 업무 세계가 우리 조직의 사용 분포를 대표한다는 보장은 없다. 근거 강도: 공식 학회 논문 내 높음, 운영 일반화 중간 이하.

### 평가자와 벤치마크 자체를 검증 대상으로 삼는다

ARES의 사람 기준 보정과 SeedRG의 검색 의존성 검사가 서로 다른 오류를 겨냥한다. 최신 보조 자료인 [AGO AI Quality Gate](https://arxiv.org/abs/2610.01218v1) — 2026-10-01, 제출본이며 NFMCP 2026 워크숍 채택 표기 — 도 도메인별 평가자 검증과 불확실성을 다룬다. 현재 초록·메타데이터 수준으로 확인했으므로 핵심 방법론의 근거로 삼지 않는다. 최신 출판일 자체가 우선순위의 이유는 아니다.

## 우리 RAG에 대한 초기 구성안

아래는 논문에서 정한 표준이 아닌 **논의를 시작할 설계 제안**이다. 현재 문서 분야, 사용자, 질문 로그와 예산은 아직 확인되지 않았다.

### 역할이 다른 세 평가셋을 관리한다

| 평가셋 | 내용 | 용도 |
| --- | --- | --- |
| 사람 검증 기준셋 | 실제 사용자 질문, 질문 당시 의도·조건, 확인한 답과 근거 | 평가자 검증과 최종 시스템 선택 |
| 합성 확장셋 | 기준 질문의 업무 유형을 따르는 생성 질문, 자동 검사와 층화 표본 검토 | 설정 탐색과 넓은 범위의 회귀 검사 |
| 도전셋 | 복합 근거, 무답, 모호성, 구버전 충돌, 표·숫자, 잡음 | 실패 원인과 검색 의존성 진단 |

사람 검증 기준셋 안에서도 프롬프트·평가자 선택에 사용하는 개발 표본과 보지 않는 최종 테스트를 분리한다. 합성 확장셋은 새로운 문서를 다룰 때 반복 생성할 수 있지만, 회귀 비교 시에는 해당 버전을 고정한다. 변형 질문과 원본은 같은 그룹으로 분할해 누출을 줄인다.

### 생성 과정

1. **사용자·업무 유형 정의:** 로그가 있으면 비식별화 후 유형·빈도·실패 사례를 표본화한다. 로그가 없으면 업무 담당자가 실제 필요를 먼저 기술한다. 문서를 읽고 바로 질문을 쓰는 방식만으로 시작하면 문서 표현을 과도하게 따라갈 수 있다.
2. **코퍼스 스냅샷 고정:** 원문·버전·효력일·접근 범위를 기록한다. 답변 가능 여부는 이 범위 안에서 정의한다.
3. **근거 선택과 질문 생성:** 단일 근거, 비교, 조건 결합, 여러 문서 종합 등을 나눈다. 복합 질문은 하나의 근거만으로 풀리지 않는지도 점검한다.
4. **답과 라벨 생성:** 정답 문장 하나 외에 필수 주장·수용 가능한 변형·근거 위치·답변 또는 재질문 또는 거절해야 할 조건을 적는다.
5. **품질 검사:** 근거의 실제 존재, 정답의 근거 지지, 과도한 단어 복사, 중복, 모호성, 잘못된 전제, 버전 충돌을 확인한다. 생성과 다른 평가자를 쓸 수 있지만 사람 검토의 대체 증명은 아니다.
6. **검색 없는 실행과 정답 근거 제공 실행 비교:** 전자는 기존 지식에 의존하는 정도, 후자는 답변 생성 단계의 상한에 대한 단서를 준다. 운영 대표셋에서 검색 없이 풀리는 문항을 모두 삭제하지 말고 별도로 태깅한다.
7. **보류한 실제 질문으로 합성셋 검증:** 평균 점수 외에 여러 시스템의 순위와 유형별 승패가 같은지 본다.

특정 retriever가 원문을 다시 찾는 문항만 남기는 필터는 그 retriever가 잘하는 질문에 편향될 수 있다. 원문으로 답할 수 있는지 검사하는 것과 현재 retriever가 찾는지 검사는 분리한다.

### 권장 레코드

```text
id, question, user_intent, assumptions
origin(real/synthetic/expert), parent_question_id
scenario, language, domain, difficulty
corpus_snapshot, as_of_date
expected_action(answer/clarify/abstain)
reference_answer, required_claims, acceptable_variants
evidence_sets[{doc_id, doc_version, page_or_section, source_span}]
review_status, reviewer, label_provenance
generator_version, prompt_version, split, dataset_version
```

`evidence_sets`는 여러 대체 근거 조합을 표현할 수 있어야 한다. 고정 chunk ID만 정답으로 저장하면 청킹을 바꿀 때 공정한 비교가 어렵다. 원문 위치를 보존하고 각 청킹 결과에 다시 매핑하는 방식을 제안한다. 실제 사용되는 청크·검색 결과·답변·평가자 버전은 실행 기록에 별도로 저장한다.

### 검색과 생성 평가를 나눠 본다

| 평가 대상 | 초기 지표 제안 | 해석 주의 |
| --- | --- | --- |
| 검색 | 근거 recall@k, graded nDCG@k, 복합 질문의 완전 근거 확보율 | 미판정 문서를 자동으로 무관하다고 두지 않기 |
| 최종 컨텍스트 | 동일 토큰 예산에서 필수 근거 보존율 | 큰 청크·많은 토큰이 유리해지는 조건 통제 |
| 답변 | 필수 주장 정확성·완전성, 실제 제공 컨텍스트에 대한 충실성, 인용 지지 여부 | 충실한 답변도 불완전하거나 구버전일 수 있음 |
| 무답·모호성 | 잘못 답하는 비율, 올바른 답변 유보/재질문 비율 | 무조건 거절하는 시스템을 보상하지 않기 |
| 평가자 | 사람과의 유형별 일치, 오류 유형, 시스템 순위 일치 | 전체 정확도 하나로 드문 중대 오류를 가리지 않기 |

세부 진단의 보조 독서로 [RAGChecker](https://arxiv.org/abs/2408.08067)를 권한다. 주장 단위로 검색과 생성 오류를 나눠 보는 접근이다. 이 표는 해당 논문의 지표 목록을 그대로 옮긴 것이 아니라 우리 용도에 맞춘 제안이다.

관련 문서 라벨을 만들 때 BM25·dense·hybrid·reranker 등 여러 검색 결과를 합쳐 판정하는 pooling을 고려한다. 생성에 사용한 원문 하나만 정답 취급하면 다른 유효 근거를 놓친다. 모든 관련 문서를 판정하지 못했다면 recall/nDCG의 불완전 라벨 한계를 결과에 적는다.

### 첫 검증 실험

시작 규모의 예로 사람 검증 질문 100–200개, 합성 질문 500–1,000개를 제안한다. 통계적 충분성을 보장하는 수치가 아니다. 업무 유형별 검토 가능량으로 조정하고, 개발용과 최종용을 미리 나눈다.

- **검색 실험:** 생성 모델을 고정하고 BM25, dense, hybrid, hybrid+reranker 등을 비교한다. 가능한 한 생성 조건과 컨텍스트 토큰 예산을 통제한다.
- **생성 실험:** 동일 검색 컨텍스트에 여러 생성 모델을 적용한다. 평가용 질문·정답을 만든 모델과 평가자의 관계도 기록한다.
- **판단:** 보류한 사람 기준셋과 합성셋의 시스템 순위, 최상위 시스템 선택, 업무 유형별 승패를 비교한다. Kendall 순위 상관만으로 결론 내리지 말고 질문별 paired 차이와 신뢰구간도 확인한다. 세션·원문에서 파생된 질문은 재표집 시 같은 그룹으로 취급한다.
- **불일치 시:** 질문이 지나치게 구체적인지, 답 스타일을 보상하는지, 복합 업무가 누락됐는지 분석하고 개발셋에서 생성법을 수정한다. 최종셋을 보고 반복 조정하면 새 홀드아웃이 필요하다.

## 남은 불확실성

- 한국어 사내 문서와 사용자 질문에서 위 결과가 재현되는지는 이 자료들만으로 알 수 없다.
- 문서 종류, 표·스캔 비중, 시간에 따른 정답 변경, 질문 로그 유무에 따라 필요한 시나리오가 달라진다.
- 무답 질문은 코퍼스 범위 전체를 충분히 확인해야 하므로 특정 한 문서에 없다는 이유만으로 생성하면 안 된다.
- 생성 모델·평가 모델을 바꿨을 때 과거 점수와 비교하려면 평가자 버전 고정 또는 교차 채점이 필요하다.
- 실제 사용자 성공률·채택률과 오프라인 점수의 관계는 별도 운영 검증이 필요하다.
