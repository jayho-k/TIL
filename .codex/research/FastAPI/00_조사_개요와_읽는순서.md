> 작성일: 2026-07-24  
> 범위: FastAPI 애플리케이션의 일반적인 실행 모델, hang 원인, 예방과 운영 진단  
> 범위 밖: 이 저장소의 특정 FastAPI 코드 평가·수정. 이 조사 노트는 특정 프로젝트에 대한 코드 리뷰가 아니다.

## 이 조사에서 말하는 `hang`

사용자가 "FastAPI가 hang 걸렸다"고 말할 때는 보통 아래 중 하나다. 실제 deadlock만 뜻하지 않는다.

| 분류 | 실제로 일어나는 일 | 겉으로 보이는 증상 |
| --- | --- | --- |
| 이벤트 루프 block | 이벤트 루프 thread가 동기 I/O·CPU 작업을 실행 중 | 같은 worker의 거의 모든 요청이 함께 멎음 |
| thread pool 대기 | 동기 endpoint/dependency가 worker thread token을 기다림 | 동기 경로만 매우 느려짐 |
| connection pool 대기 | DB·HTTP connection을 얻지 못함 | 특정 의존성을 쓰는 API가 timeout 직전까지 대기 |
| 외부 의존성 무한 대기 | DB, DNS, HTTP, 파일, GPU 등이 응답하지 않음 | 일부 요청이 끝나지 않고 자원을 계속 점유 |
| lock/semaphore deadlock | 필요한 lock/token을 서로 기다리거나 반환하지 않음 | 재현 조건에서 요청이 영구 대기 |
| 과부하 queueing | 처리율보다 유입량이 커서 대기열이 계속 증가 | 시간이 갈수록 p95/p99 latency가 증가 |

따라서 첫 질문은 "thread가 부족한가?"가 아니라 **어느 자원 앞에서 대기하는가?** 이다.

## 가장 먼저 고쳐야 할 두 가지 오해

### 1. Python에 thread pool이 없는가?

아니다. Python 표준 라이브러리에는 `concurrent.futures.ThreadPoolExecutor`가 있고, `asyncio`도 executor에 작업을 넘길 수 있다. FastAPI는 동기 path operation과 동기 dependency를 호출할 때 외부 thread pool에서 실행한다.

핵심은 Python에 thread가 있느냐가 아니라, **FastAPI의 `async def` 요청은 기본적으로 요청당 thread를 하나 빌리는 모델이 아니라 이벤트 루프의 coroutine task 모델**이라는 점이다.

### 2. `async def`면 항상 빠르고 hang이 없는가?

아니다. coroutine은 `await` 지점에서만 다른 task에 실행 기회를 준다. `async def` 안에서 `time.sleep()`, 동기 HTTP 호출, 동기 DB 호출, 이미지 변환, 긴 Python CPU loop를 실행하면 해당 worker의 이벤트 루프가 멈춘다. 이 문제가 FastAPI에서 가장 위험한 hang 유형이다.

아래 내용은 2026-07-24에 확인한 **1차 공식 문서**를 기준으로 한다. FastAPI/Starlette/AnyIO는 함께 버전이 움직이므로 실제 운영 환경에서는 lock file 또는 배포 image의 패키지 버전도 별도로 확인해야 한다.

| 영역 | 기준 문서 | 신뢰도 | 이 조사에서 확인한 사실 |

## 한 장 요약

```text
클라이언트
  → Uvicorn worker process
      → event loop
          → async endpoint / async dependency
              → await 가능한 I/O
          → sync endpoint / sync dependency
              → AnyIO worker thread pool (기본 40 token)
                  → DB/HTTP/file 등 외부 자원

각 화살표의 대기열은 서로 다르다.
event loop가 멈춘 문제, thread pool이 찬 문제, DB connection이 없는 문제는
증상과 해결법이 다르다.
```
