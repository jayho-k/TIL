# thread pool, connection pool, semaphore: 서로 다른 대기열

> 선행: [요청 실행 모델](./01_FastAPI_요청_실행_모델.md), [이벤트 루프 blocking](./02_이벤트루프_blocking과_hang.md)  
> 핵심: pool을 하나로 보지 않는다. 어떤 자원을 빌리려다 기다리는지에 따라 진단과 설정이 달라진다.

## 1. FastAPI 요청 주변의 대기열 지도

```text
inbound connection/request
  └─ Uvicorn concurrency/backlog
       └─ event-loop task
            ├─ AnyIO thread token ──> sync endpoint/dependency/file task
            ├─ DB connection       ──> query / transaction / DB lock
            ├─ HTTP connection     ──> connect / read / write / remote service
            └─ app semaphore       ──> GPU, vendor API, CPU job 등의 정책상 한도
```

어느 하나가 포화돼도 요청은 "멈춘 것"처럼 보인다. 그러나 다음은 전혀 다른 사건이다.

| 기다리는 자원 | 대표 증상 | 잘못된 흔한 처방 |
| --- | --- | --- |
| event loop | 같은 worker의 async route까지 지연 | thread 수만 늘림 |
| AnyIO thread token | sync route/dependency/file 작업 지연 | DB pool만 증설 |
| DB connection | DB 경로가 pool timeout까지 대기 | thread token만 증설 |
| DB lock | 특정 query가 lock 해제까지 대기 | connection pool을 무제한 증설 |
| HTTP connection | 특정 downstream 호출이 pool timeout | worker 수만 증설 |
| semaphore | 특정 비싼 기능이 순서 대기 | timeout 없이 semaphore 수만 키움 |

## 2. AnyIO thread pool 포화

Starlette는 동기 endpoint와 동기 dependency를 `anyio.to_thread.run_sync`로 실행한다. 기본 limiter는 40 token이다. 이 token은 process마다 존재하며 다양한 동기 작업이 공유한다.

```text
40개의 sync 작업이 모두 외부 API 응답을 기다리는 상황

sync request 1..40  → worker thread 실행 중 (각각 60초 대기)
sync request 41    → thread token을 얻기 전까지 event loop task에서 대기
sync request 42    → 동일
```

여기서 request 41이 event loop를 block하는 것은 아니다. event loop는 살아 있으나, sync 작업을 실행할 **용량 token**이 없다. 따라서 순수 async endpoint는 아직 응답할 수 있다.

### 포화를 만드는 작업

- 느린 동기 DB driver/ORM 호출
- `requests`, 동기 cloud SDK, 동기 파일 API
- sync dependency에서 하는 인증·검증·파일 읽기
- `UploadFile`, `FileResponse` 관련 thread 작업
- sync `BackgroundTask`
- timeout 없는 legacy library 호출

### "기본 40"을 100으로 올리면 되는가?

아니다. 늘릴 수는 있지만 첫 번째 해결책이 아니다.

- thread마다 stack·scheduler 비용·메모리가 든다.
- thread를 늘리면 DB/API에 동시에 보내는 요청도 늘어난다.
- 병목이 DB connection 20개라면 thread 100개 중 80개는 DB connection을 기다릴 뿐이다.
- CPU-bound 작업을 많이 넣으면 GIL 경쟁과 context switching으로 event loop 지연도 커질 수 있다.

먼저 "왜 오래 점유되는가"를 timeout, downstream latency, thread stack으로 확인한다. token 상향은 부하 테스트를 거쳐 전체 자원 예산 안에서만 결정한다.

## 3. DB connection pool 고갈

DB pool은 thread pool과 다르다. thread 하나가 DB query를 하려면 다시 DB connection을 빌린다. pool의 모든 connection이 checkout 상태이면 다음 요청은 DB connection을 기다린다.

SQLAlchemy `QueuePool`의 대표 설정은 다음과 같다.

```python
engine = create_engine(
    database_url,
    pool_size=20,
    max_overflow=0,
    pool_timeout=2,
    pool_pre_ping=True,
)
```

- `pool_size`: 유지할 connection 수
- `max_overflow`: 순간적으로 추가 허용할 connection 수
- `pool_timeout`: connection을 빌리기 위해 기다릴 최대 시간
- `pool_pre_ping`: 오래 idle 상태였던 connection의 생존 확인에 도움

`pool_timeout`이 없다면 문제를 오래 기다린 뒤 늦게 발견한다. timeout은 응답 속도를 높이는 마법이 아니라, **대기열이 무한히 성장하지 않게 실패를 빠르게 드러내는 경계**다.

### DB pool 포화의 진짜 원인

1. connection/session을 반환하지 않는 leak
2. 긴 transaction
3. 느린 query 또는 full scan
4. DB lock wait
5. worker 수 증가에 따른 총 connection 수 증가
6. downstream DB 자체의 connection limit 부족

특히 worker가 여러 개면 총량을 계산해야 한다.

```text
최대 DB connection 수 ≈ worker 수 × (pool_size + max_overflow)

예: worker 4 × (20 + 5) = 최대 약 100 connections
```

애플리케이션 하나만 보지 말고, 같은 DB를 쓰는 다른 서비스와 DB reserve connection까지 포함해 예산을 정한다.

### DB lock wait는 pool 문제와 다르다

connection을 얻은 뒤에도 query가 row/table lock을 기다릴 수 있다. 이때 pool을 늘리면 기다리는 connection만 더 많아진다. PostgreSQL이라면 `statement_timeout`, `lock_timeout`, 필요 시 transaction timeout을 application role 또는 request 성격에 맞게 설정한다.

## 4. outbound HTTP connection pool 고갈

HTTP client도 keep-alive connection pool을 가진다. 비동기 HTTP client를 쓴다고 connection이 무한한 것은 아니다.

HTTPX는 다음 대기 시간을 분리한다.

| timeout | 의미 |
| --- | --- |
| connect | TCP/TLS 연결을 만드는 시간 |
| read | response data chunk를 기다리는 시간 |
| write | request data를 보내는 시간 |
| pool | client connection을 빌리기 위해 기다리는 시간 |

```python
import httpx

timeout = httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=0.5)
limits = httpx.Limits(max_connections=50, max_keepalive_connections=20)
client = httpx.AsyncClient(timeout=timeout, limits=limits)
```

pool timeout이 발생한다면 "HTTP client가 느린 것"이 아니라 보통 다음 중 하나다.

- remote server가 느려 connection이 오래 반환되지 않음
- response body를 끝까지 소비/close하지 않아 connection이 반환되지 않음
- client가 너무 적은 connection만 허용함
- inbound 동시성이 downstream capacity보다 큼
- 요청마다 client를 새로 만들어 pooling 자체가 깨짐

## 5. semaphore는 pool이 아니라 애플리케이션 정책

DB/HTTP pool은 client library가 관리하는 연결 자원이다. 반면 `asyncio.Semaphore`는 서비스가 직접 정하는 **동시 실행 budget**이다.

```python
gpu_slots = asyncio.Semaphore(2)

async def run_inference(payload):
    async with gpu_slots:
        return await inference_client.generate(payload)
```

GPU처럼 동시에 2개만 안정적으로 처리할 수 있는 자원에는 필요하다. 그러나 다음이 없으면 새 hang 원인이 된다.

- semaphore 획득 대기 timeout
- 실제 작업 timeout
- `finally` 또는 context manager를 통한 확실한 release
- queue가 길 때의 거절 정책(429/503 또는 비동기 job 전환)

**중요:** semaphore 값은 throughput을 높이는 숫자가 아니라 downstream을 보호하는 계약이다. "대기가 길다"고 무작정 값을 키우면 GPU OOM, rate limit, DB overload로 바뀔 수 있다.

## 6. pool 순서가 만드는 연쇄 대기

가장 위험한 형태는 상위 자원을 잡은 채 하위 자원을 오래 기다리는 것이다.

```text
thread token 획득
  → DB connection 대기
      → DB lock 대기
          → 외부 API 호출 대기
```

이런 요청이 많아지면 thread token과 DB connection이 함께 장시간 점유된다. 예방 원칙은 다음과 같다.

- transaction 안에서 외부 HTTP 호출을 하지 않는다.
- DB connection을 빌린 뒤 불필요한 CPU/네트워크 작업을 하지 않는다.
- lock을 잡은 채 오래 `await`하지 않는다.
- 각 경계마다 timeout을 둔다.
- 낮은 용량 자원(DB/GPU/vendor API)보다 inbound concurrency가 과도하지 않게 제한한다.

## 7. pool sizing은 하나의 숫자가 아니라 예산표다

예시는 다음과 같이 계산한다.

```text
DB가 이 API에 허용한 동시 query: 30
worker 수: 3
worker당 DB pool 상한: 10 (총 30)

외부 vendor API의 안전 동시 호출: 12
worker 전체 semaphore 합: 12

sync legacy I/O의 안전 동시 호출: 24
AnyIO default 40을 그대로 쓰지 않고, 별도 limiter 또는 진입 제한을 검토
```

이 값은 CPU core 수만으로 정할 수 없다. downstream capacity, 평균/최악 latency, timeout, 요청당 fan-out, 메모리, retry 정책을 함께 본다.

## 8. 핵심 교훈

> event loop, thread token, DB connection, HTTP connection, semaphore는 서로 교환 가능한 자원이 아니다. pool 하나를 키우기 전에 어떤 queue가 증가하는지 먼저 측정한다.
