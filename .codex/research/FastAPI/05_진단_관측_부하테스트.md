# FastAPI hang 진단: 증상에서 대기 지점까지

> 선행: [이벤트 루프 blocking](./02_이벤트루프_blocking과_hang.md), [pool 대기열](./03_스레드풀_커넥션풀_대기열.md), [timeout/backpressure](./04_timeout_cancellation_backpressure.md)  
> 목표: "느리다"를 event loop, thread token, DB/HTTP pool, downstream, lock 중 하나로 좁힌다.

## 1. 장애 때 가장 먼저 할 분류

### 질문 1: 모든 endpoint가 느린가?

- **가벼운 async liveness endpoint까지 느리다**: event loop blocking, CPU saturation, process stall을 먼저 의심한다.
- **일부 endpoint만 느리다**: 해당 endpoint의 dependency, DB/HTTP pool, semaphore, downstream을 먼저 본다.

### 질문 2: async 경로와 sync 경로의 차이는?

- sync endpoint·sync dependency만 느리고 async liveness는 빠르다: AnyIO thread pool token 포화 가능성이 높다.
- async HTTP/DB endpoint만 느리다: downstream latency, connection pool, DB lock, timeout 설정을 본다.

### 질문 3: CPU는 높은가, 낮은가?

| 상태 | 우선 가설 |
| --- | --- |
| worker CPU 높음 + event-loop lag 높음 | CPU-bound loop, serialization, 압축/이미지 변환, GIL contention |
| CPU 낮음 + in-flight 요청 증가 | 외부 I/O 대기, DB/HTTP pool 대기, lock wait |
| memory 증가 + latency 증가 | 무한 queue, 큰 body/response, task 누수, connection leak |
| file descriptor 증가 | connection/response body/socket leak |

### 질문 4: 지연은 어느 시점부터 발생했는가?

- 배포 직후부터: startup/lifespan, 설정 오류, connection 실패
- 특정 downstream 배포·장애 이후: 외부 HTTP/DB timeout, retry storm
- 트래픽 증가 이후: unbounded concurrency, pool 포화, worker CPU/memory 부족
- 시간이 갈수록: leak, 긴 transaction, idle connection, queue 성장

## 2. 반드시 수집할 지표

### HTTP/API 레벨

- request rate, in-flight request 수
- status code(특히 429, 499/클라이언트 취소, 503, 504, 5xx)
- p50/p95/p99 latency와 endpoint별 latency
- request/response body size
- timeout, cancellation, retry 횟수

평균 latency만 보면 hang을 놓친다. 대기열 문제는 평균보다 p95/p99에서 먼저 드러난다.

### 이벤트 루프 레벨

- event-loop lag: 예정된 heartbeat가 실제 실행된 시간의 지연
- 실행 중 task 수와 장시간 살아 있는 task
- slow callback 경고
- worker별 CPU utilization

event-loop lag가 증가하면 "loop가 일할 기회를 못 얻는다"는 강한 신호다. 원인은 동기 I/O일 수도, CPU-bound일 수도 있다. lag 자체만으로 원인을 확정하지 말고 CPU·stack trace·endpoint span과 결합한다.

### thread pool 레벨

- AnyIO limiter의 `total_tokens`, `borrowed_tokens`
- process thread count
- sync endpoint/dependency의 queue wait time
- thread에서 실행 중인 외부 호출의 latency·timeout

`borrowed_tokens`가 한계 근처에 오래 머무르면 sync 작업이 pool 대기열을 만들 가능성이 높다. limiter 내부 지표를 노출할 때는 framework 버전별 public API와 보안 정책을 확인한다.

### DB 레벨

- pool checked-out/idle/overflow/wait time
- connection checkout timeout 횟수
- query latency, slow query 수
- active transaction 시간
- DB lock wait와 blocking query
- DB server connection 수와 max connection 대비 사용률

DB connection을 못 얻는 것과 connection을 얻은 뒤 lock을 기다리는 것은 다른 대시보드로 봐야 한다.

### outbound HTTP 레벨

- host/route별 connect/read/write/pool timeout
- client pool 사용량과 queue wait
- remote status code·latency
- retry count와 retry로 증가한 요청량
- open connection/file descriptor 수

## 3. 분산 trace는 "대기 시간의 위치"를 보여 준다

request span 하나만 있으면 "전체 3초"만 보인다. 다음 span을 나누면 병목을 위치로 볼 수 있다.

```text
HTTP server request: 3.0s
  ├─ auth dependency: 0.02s
  ├─ DB pool checkout: 0.80s
  ├─ SQL query: 0.15s
  ├─ partner HTTP pool checkout: 0.01s
  └─ partner HTTP read: 1.90s
```

thread/semaphore 대기도 별도 span 또는 metric으로 남긴다. "DB query가 0.15초"인데 request가 3초라면 DB pool checkout 또는 다른 대기열이 원인일 수 있다.

## 4. 실제 장애 때의 진단 순서

1. **영향 범위 확인**: worker 전체인가, 특정 route인가, 특정 tenant/downstream인가?
2. **빠른 상태 확인**: worker CPU/RAM/FD, in-flight, event-loop lag, 5xx/timeout 비율.
3. **queue 선택**: thread token, DB pool, HTTP pool, semaphore 중 어느 wait가 증가했는지 확인.
4. **downstream 확인**: DB lock/slow query, remote HTTP latency·error, DNS/network 문제.
5. **stack 확보**: 오래 실행 중인 worker thread와 asyncio task stack을 확보한다.
6. **완화**: concurrency limit, traffic shed, retry 축소, unhealthy worker restart, downstream circuit open처럼 현재 load를 낮춘다.
7. **근본 원인 검증**: 재현 가능한 부하 테스트와 trace로 가설을 검증한다.

restart는 일시 완화일 수 있지만, lock leak·connection leak·무한 timeout을 숨길 수 있다. restart 전후의 stack과 pool 상태를 남겨야 다음 장애에서 원인을 찾을 수 있다.

## 5. 의도적으로 재현해 볼 세 가지 실험

### 실험 A: event loop blocking

`async def` route 안에서 `time.sleep(2)`를 호출하고, 동시에 가벼운 async `/live` 요청을 보낸다. `/live`도 함께 지연되면 event-loop block의 전파 범위를 체감할 수 있다.

그 뒤 `await asyncio.sleep(2)`로 바꿔 차이를 비교한다.

### 실험 B: thread pool 포화

동기 `def` route에서 timeout 없는 `time.sleep(10)` 또는 느린 동기 I/O를 실행하고, 40개를 넘는 동시 요청을 보낸다. 41번째 이후 요청의 queueing을 관찰한다.

이때 async `/live`가 빠른지, sync route만 밀리는지 비교한다. 실제 서비스에서는 `time.sleep` 대신 timeout을 둔 test double을 사용한다.

### 실험 C: connection pool 포화

작은 DB 또는 HTTP connection limit을 설정하고, connection을 오래 점유하는 요청을 동시에 보낸다. `pool_timeout`을 설정했을 때 오래 hang하는 대신 명확한 오류와 metric이 생기는지 확인한다.

실험의 목적은 숫자 40·20을 외우는 것이 아니라, **각 pool의 포화가 다른 증상으로 보인다**는 점을 익히는 것이다.

## 6. 부하 테스트 설계 원칙

- 정상 평균 부하만이 아니라 burst를 넣는다.
- downstream latency를 의도적으로 느리게 한다.
- timeout, retry, cancellation이 동시에 발생하는 경우를 넣는다.
- 요청당 fan-out(한 요청이 외부 API를 몇 번 부르는지)을 포함한다.
- 작은 payload와 최대 허용 payload를 모두 쏜다.
- 목표는 최대 RPS가 아니라 SLO 안에서 유지되는 concurrency와 failure mode를 찾는 것이다.

부하 테스트 결과에는 최소한 다음을 남긴다.

```text
환경/worker 수/CPU·memory
FastAPI·Starlette·AnyIO·Uvicorn 버전
DB/HTTP pool과 timeout 설정
request mix·payload size·동시 사용자 수
p50/p95/p99, error/timeout/retry, event-loop lag, pool wait
```

## 7. 증상-원인 빠른 매핑

| 증상 | 우선 확인 | 가능한 완화 |
| --- | --- | --- |
| `/live`까지 멎음 | event-loop lag, CPU, task stack | blocking 경로 차단, CPU 작업 격리 |
| sync API만 지연 | AnyIO token 사용량, thread stack | timeout·thread 작업 축소·별도 limiter |
| DB API만 지연 | pool checkout, slow query, lock wait | query/lock timeout, pool 예산 재조정 |
| 외부 연동만 지연 | HTTP pool wait, connect/read timeout | client reuse, timeout, circuit/rate limit |
| 트래픽에서만 악화 | in-flight, queue length, retry rate | limit-concurrency, semaphore, 429/503 |
| 시간이 갈수록 악화 | memory/FD/pool checkout 추세 | leak 분석, max requests/restart는 임시 완화 |

## 8. 이 장의 결론

> hang은 하나의 metric으로 찾지 않는다. 영향 범위, event-loop lag, CPU, 각 pool의 checkout/wait, downstream latency를 함께 보면 대기 위치를 좁힐 수 있다.
